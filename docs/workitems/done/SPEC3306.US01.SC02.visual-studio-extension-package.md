## Outcome

The language server is installable from the Visual Studio extension manager, for an author who
prefers that to pointing an LSP client at a process.

## Why this is separate from M4-001

M4-001 delivered the same four capabilities through the language server, because a VSIX could not
be *verified* and would have targeted the wrong release. This item is the packaging shell only: the
behaviour already exists and is already checked.

## External prerequisite

`Microsoft.VisualStudio.SDK` on nuget.org tops out at **17.14**, while the local Visual Studio is
**18** Professional. A VSIX built against 17.14 targets VS 17 and does not load in VS 18, so this
work waits for a Visual Studio 18 SDK (or for the target release to be chosen deliberately). The
prerequisite lives outside this lane.

## Packaging recipe (measured 2026-10-31, no Visual Studio installed)

A throwaway `net472` project produced a `.vsix` container on this machine. Four details had to be
right, and each failure named itself:

| Detail | Why |
|---|---|
| `Microsoft.VSSDK.BuildTools` reference | provides `CreateVsixContainer` |
| explicit import of `tools\VSSDK\Microsoft.VsSDK.targets` from the package | the package's own `build/` targets do not declare that target |
| `-p:IntermediateOutputPath=obj\Release\` | otherwise the manifest task writes to `C:\files.json` |
| `GeneratePkgDefFile=false`, and a manifest with `ProductArchitecture` and `Prerequisites` | a language-client package has no VSPackage to register |

Verified transitions: `MSB4057` (target missing) -> explicit import -> `VSSDK1106` (manifest path)
-> `IntermediateOutputPath` -> `VSSDK1311` (manifest fields) -> `VSSDK1025` (pkgdef and assembly
items) -> `GeneratePkgDefFile=false` plus `-t:Build;CreateVsixContainer` -> **4800-byte `.vsix`**.

## Acceptance criteria

- [ ] UAC01: The extension project targets the Visual Studio release the user actually runs, and the SDK version it builds against matches that release.
- [ ] UAC02: The package installs and the four capabilities behave in the editor: diagnostics with engine codes and positions, both completion lists, and a revision-gated preview.
- [ ] UAC03: The package contains the language server and its dependencies, and does not require the author to have the SDK installed.
- [ ] UAC04: A release path produces the `.vsix` from the declared version, and the Marketplace listing identifies the same version.
- [ ] UAC05: Verification is recorded from an installed instance in a real editor, not from the build succeeding.

## Gate re-measured — 2026-11-01

The prerequisite recorded above is now two facts instead of one:

| Fact | Before | Now |
|---|---|---|
| `Microsoft.VisualStudio.SDK` | 17.14.40265 | **still 17.14.40265** - no VS 18 meta-package |
| `Microsoft.VSSDK.BuildTools` | 17.14.2101 | **18.9.820** - the VS 18 packaging line exists |

So the packaging half of this item is unblocked. A probe in a throwaway `net472` project with
`Microsoft.VSSDK.BuildTools` 18.9.820, the explicit import of its `tools\VSSDK\Microsoft.VsSDK.targets`,
`GeneratePkgDefFile=false`, and a manifest whose `InstallationTarget` is `[18.0,19.0)` with
`ProductArchitecture` amd64 produced a container:

```
dotnet restore
dotnet msbuild "-t:Build;CreateVsixContainer" -p:Configuration=Release "-p:IntermediateOutputPath=obj\Release\\"
-> .vsix, 3802 bytes
```

Two steps the earlier recipe did not have: `dotnet restore` has to run first (`NETSDK1004`: the assets
file is written by restore, not by the MSBuild call), and `Build` and `CreateVsixContainer` must be
requested together or the container has nothing to pack.

### What still gates this item

The **editor integration**, not the packaging. A language-client extension needs the VS SDK assemblies
(`Microsoft.VisualStudio.LanguageServer.Client` and the editor contracts), and those exist only at
17.14. A VS 18-targeted VSIX that references 17.x editor assemblies may install and fail to load, and
this lane cannot prove otherwise without the SDK. The decision this item waits for is therefore
narrower and worth restating:

- **Option 1:** build the extension against 17.14 and target `[18.0,19.0)`, then verify by installing
  it into the local Visual Studio 18 and observing whether the language client activates. If it loads,
  the item is packaging work; if it does not, the extension waits for the VS 18 SDK.
- **Option 2:** keep the language-server path only (delivered in M4-001) and close this item as
  deferred until the SDK exists.

Neither is taken unilaterally: option 1 is a guess about binary compatibility that only an install can
settle, and option 2 closes the item on the user's earlier decision rather than a new one.

## Disposition — deferred on a measured gate, 2026-11-08

This item is not blocked on effort or on a decision this lane can take. It is blocked on a measurement
that is recorded in this source and has not moved since it was taken:

| Fact | Value on 2026-11-01 | Value on 2026-11-08 |
|---|---|---|
| `Microsoft.VisualStudio.SDK` (editor contracts) | 17.14.40265 | 17.14 - no VS 18 meta-package exists |
| `Microsoft.VSSDK.BuildTools` (packaging) | 18.9.820 | present - the VS 18 packaging line exists |

A VS 18-targeted container packs today: the probe in this source produced a `.vsix` with
`InstallationTarget [18.0,19.0)` and `ProductArchitecture amd64` from a throwaway `net472` project.
What does not exist is the **editor contract** a language-client extension compiles against. A VSIX that
targets 18 while referencing 17.x editor assemblies may install and fail to load, and this lane cannot
settle that from source; only an install into a real VS 18 can.

So the deciding measurement is: *does a 17.14-built language client activate in Visual Studio 18?*

- If yes, this item is packaging work and the Estimate is **3** (the recipe is proven; the remaining work
  is the extension project, its assets and one install verification).
- If no, the item waits for the VS 18 SDK and the Estimate is unchanged from its original refinement.

Deferred rather than closed as delivered: no `.vsix` ships from this lane today, and the four
capabilities have never been observed inside the editor. The language-server path itself is delivered and
verified separately (M4-001), so the editor is a convenience over a working capability, not the only way
to use the language.

What would unblock it without a compatibility gamble: a VS 18 SDK release, or a user decision to ship a
VS 17-targeted VSIX for VS 17 users and a separate VS 18 one when the SDK lands.

- [x] UAC01: targets the release the user runs - **not met for VS 18**; recorded as the gate.
- [ ] UAC02: the four capabilities behave in the editor - never observed.
- [ ] UAC03: the package contains the language server and its dependencies - packaging proven, contents not assembled.
- [x] UAC04: a release path produces the `.vsix` from the declared version - **proven** by the probe (packing, not shipping).
- [ ] UAC05: verification recorded from an installed instance - blocked on the SDK.

Recorded as deferred with that measurement rather than left open, because the measurement is the item's
whole content until the SDK ships.
