## Outcome

The host knows which credential made a call and from where, without trusting anything the client asserts about itself, so an incident can be attributed and a spoofed identity header cannot grant authority.

## Problem

Tinytools has no account system, so the backend scope's account/device/IP provenance has no direct equivalent. What it does have is one credential and a transport peer; those must be recorded and the untrusted inputs must be named.

## Acceptance criteria

- [x] UAC01: An accepted call records the kind of credential that made it.
- [x] UAC02: An accepted call records the transport peer and never a client-supplied address.
- [x] UAC03: A caller that asserts an identity header without a credential is refused.
- [x] UAC04: A client-supplied forwarding address never appears in the recorded provenance.
- [x] UAC05: After the configured key changes, the superseded key is refused.
- [x] UAC06: After the configured key changes, the new key is accepted without a restart.
- [x] UAC07: Refused calls are recorded too, so a refusal is attributable.

## Scenario contract

Given a production test host whose `Tinytools:ApiKey` value can change while it runs
(`TemplateApiFactory` with a `MutableSettingsSource`), When one accepted call, one call that asserts
identity and forwarding headers without a credential, and calls made before and after the key is
replaced all run, Then the scenario captures, by name:

| Captured case | Observed value |
|---|---|
| `Credential` | the credential kind of the accepted call, `api-key` |
| `Peer` | the transport peer recorded for that call |
| `SpoofStatus` | the status of the spoofed anonymous call, 401 |
| `Peers` | every distinct peer recorded, joined with `|` |
| `SupersededStatus` | the status of the retired key after rotation, 401 |
| `RotatedStatus` | the status of the new key after rotation, 200 |
| `Refusals` | how many recorded entries carried no credential |

Given construction and the When HTTP calls stay visible in
`SC03_RecordsProvenanceWithoutTrustingTheCaller.cs`; `EndpointProtectionUseCase` only names the
captured results. One Fact per stable UAC01-UAC07.

## Divergence from the backend scope

The backend surface is `/api/plugins/{**path}` behind an account, device and IP model owned by the Auth
lane. Tinytools has one credential and seven template operations, and it deliberately refuses plugin
paths (`SPEC3315-US02-SC02`). Where the backend criterion depends on accounts or devices, this scope
requires the equivalent on this surface - credential scoping, provenance of the configured key, and
untrusted client headers - rather than inventing an account system here.

### What it took

- `CallerProvenanceMiddleware` records the transport peer and whether the configured header was
  present, before authorization runs, so refusals are attributable. It reads nothing the caller
  asserts about itself.
- `CallerProvenanceLog` is a bounded 256-entry in-memory record with no request content - enough to
  attribute an incident, not enough to become a data store.
- Rotation is proven by a mutable configuration source in the test host
  (`MutableSettingsSource`), because `ApiKeyHandler` reads the configured value per request. That
  property was true and untested; it is now the contract.

The store is process-local and is not a substitute for the tracing and audit work SC10 owns.
