## Outcome

The shared workitem mirror can prove that this repository's issues still carry the right identity,
without replacing the evidence text they already carry - so `--verify-only` answers a question the
lane can act on instead of reporting drift that nobody intends to fix by rewriting 48 issues.

## Problem

`eng/workitems.py --apply` regenerates each managed issue from its source, and `--verify-only` failed
while any issue differed. This repository's issues predate the managed convention, so all of them
differ. Measured at SPEC3318 (delivery record) with a throwaway patched copy of the tool:

- `--dry-run` -> `ok=true items=47`, every action `update`, **zero create**, so identity is correct.
- `--dry-run --preserve-body` -> still `update=47`, so the body is not the only difference.
- Comparing `#10`: the tool wants `SPEC3300-US03-SC02: Preserve comparison operator precedence`, the
  issue is titled `Operator precedence bug in TinyTemplateEngine condition evaluation`; state and
  label sets differ too.

Applying the global plan would therefore rename and relabel 47 issues as well as replace their bodies.
Neither is authorised by any workitem.

Two things turned out to be true when the tool was actually opened:

1. `--verify-only` already existed; it planned as usual and raised `Managed remote state has drift`
   whenever any item was not `unchanged`, without saying which item or which field.
2. The three preserve flags would have fixed a symptom. The defect was that one exit code meant two
   unrelated things: "the mirror cannot identify this workitem" and "the issue text is out of date".

## Contract (delivered, with the write path deliberately deferred)

| Kind | Meaning | Exit |
|---|---|---|
| identity drift | the marker resolves to no issue, to several, or the scope sits on an unmarked issue | **1** - nothing may be applied until fixed |
| content drift | the resolved issue's title, body, state or labels differ from a regenerated projection | **0**, reported per item with the differing fields |

`--verify-only` writes nothing. `--strict` restores the previous fail-on-any-difference behaviour, and
`--strict` without `--verify-only` is rejected rather than ignored.

Deferred, deliberately: `--preserve-body`, `--preserve-title` and `--preserve-state`. They change what
`--apply` means, no lane has needed a rewrite, and building them now would be a write-path change with
no consumer. `--apply` stays off for this repository.

### The proposal was wrong about the mechanism

`--verify-only` **already existed**: it planned as usual and raised `Managed remote state has drift`
whenever any item was not `unchanged`. Two facts make that useless on a real board:

1. every issue that predates managed identity has a different title, body and label set, so the
   answer was always "drift" - for 48 of 48 tinytools items, 658 of 658 in Builder;
2. it could not say *which* item drifted or *how*, so nobody could act on it.

The preserve flags would have fixed the symptom. The defect is that one exit code meant two
completely different things.

### What changed instead

`eng/workitems.py` now separates them in `--verify-only`, which writes nothing:

| Kind | Meaning | Exit |
|---|---|---|
| identity drift | the marker resolves to no issue, to several, or the scope sits on an unmarked issue | **1** - nothing may be applied |
| content drift | the resolved issue's title/body/state/labels differ from a regenerated projection | **0**, reported per item with the differing fields |

`--strict` restores the previous fail-on-any-difference behaviour for a lane that wants it, and
`--strict` without `--verify-only` is rejected rather than silently ignored. The report gained
`mode`, `strict`, `content_drift` and `content`, and `identity` items carry `problem` and `numbers`.

Six regression tests were added to `eng/test_workitems.py`: content drift passes and names its
fields, a missing marker fails, a scope on an unmarked issue fails, duplicate markers fail, strict
fails on content drift, and verify issues only GET requests. `python -m unittest test_workitems
test_agent_hub test_backup_hub` -> **34 tests, OK**.
