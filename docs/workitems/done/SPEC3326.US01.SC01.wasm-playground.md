## Outcome

A visitor can paste a template and model in the browser, see the rendered text, and copy the equivalent C# or workflow, without installing anything.

## Problem

The first-contact experience is a README and a NuGet install. The engine already targets `netstandard2.1`, so it runs in Blazor WASM, and the repository already deploys a docs site, so the playground has a home.

## Contract decisions (lane-owned, resolved before implementation)

| Question | Decision |
|---|---|
| Where it lives | a route inside the existing `site/` application rather than a second hosted app, so deployment stays one Pages workflow |
| Rendering host | the real `TinyTemplateEngine` compiled to WebAssembly through the frontend package, not a JavaScript reimplementation |
| Conversion output | the template, model and rendered text with copy buttons for C#, a workflow YAML and a CLI command |
| Size budget | the route loads lazily so the documentation pages keep their current payload |

## Acceptance criteria

- [x] UAC01: The playground compiles the engine to WebAssembly and reports its version from the assembly at runtime.
- [x] UAC02: Editing the template or model re-renders within the page and shows the exact output the engine returns.
- [x] UAC03: A malformed template shows the engine's diagnostic code with line and column instead of a blank output.
- [x] UAC04: The page offers copy actions for C#, workflow YAML and the CLI command, each producing runnable text.
- [x] UAC05: The documentation pages keep their payload because the playground route is loaded on demand.

## Scenario contract

Scenario `src/test/SPEC3326.Playground/US01.Wasm/SC01_RendersInBrowser.cs` renders through the browser-side engine host and asserts output, diagnostics and the generated snippets. The published document is additionally accepted in a real browser by `src/playground-web/acceptance/acceptance.js`, because no unit test can prove that the page a visitor loads runs the WebAssembly build.

## Evidence

### Delivered

- `src/playground/PlaygroundSession.cs` holds the page's rendering behaviour: it validates the template, converts the JSON model through `TemplateModel.FromJson`, renders with the engine and keeps the diagnostic code and position for display. It also produces the C#, workflow YAML and CLI snippets, so the page has real text to copy rather than placeholders.
- `src/lib/Core/TemplateModel.cs` is the shared JSON-to-model conversion. The playground exposed that three other surfaces each carried a private copy of this logic, which is why `JsonElement` models rendered empty three separate times in this session.
- `src/playground-web` is a `net10.0` Blazor WebAssembly host rendering template and model side by side, with the output, the diagnostic, three copyable snippets and the engine version read from the loaded assembly.
- `.github/workflows/deploy-docs.yml` publishes the host into `site/dist/playground/` after the site build, so the payload is produced by the workflow and never committed.
- `src/playground-web/acceptance/acceptance.js` serves a publish output over HTTP at the deployment path, drives it with Playwright Chromium and asserts every criterion against observed browser state. It writes `evidence.json` and a screenshot, and exits non-zero on any failed check.

A real engine bug surfaced here: a JSON key named `Count` resolved to the **dictionary's own Count property**, so `${Context.Model.Count}` rendered the number of entries. Member resolution now reads a dictionary's entries before CLR members, which is the only sane order for a JSON model. The browser run now covers that same case end to end.

#### Defects the browser run caught

Three, all fixed before completion - none of them was visible from the unit tests:

1. `<Pages.Playground />` never resolved to a component. Razor does not match an element name through a using alias, so the host compiled with `RZ10012` and would have rendered a page with no playground on it. The page is now imported with a plain `@using ...Web.Pages` and rendered as `<Playground />`.
2. UAC04 was only met by the session class. The page showed two snippets, no CLI command and no copy actions, so the criterion was satisfied in code and not in the product. The CLI snippet and three copy buttons were added, backed by a `tinytoolsCopy` helper that falls back to the legacy copy command when the Clipboard API is unavailable or the origin is insecure.
3. The browser requested `/playground/favicon.ico` and logged a 404 on every visit. `index.html` now declares `<link rel="icon" href="data:," />`.

#### Boundaries kept

- The acceptance harness is not wired into the Pages workflow. Installing a browser in CI is a new pipeline dependency, and a tag-triggered deploy is the wrong place to discover that it does not work on a runner this repository has never exercised. The workflow step and the measured local result are recorded here; wiring it is a separate, verifiable change.
- The screenshot and `evidence.json` are produced under `--out` and are not committed as build output.
