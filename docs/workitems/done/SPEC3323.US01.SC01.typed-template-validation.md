## Outcome

A `${Context.X}` that the declared model cannot satisfy becomes a build error instead of an empty string at run time.

## Problem

The source generator emits a typed `Render(Model)` from each `.tmpl`, but it does not inspect the template's variable paths. A typo therefore compiles and renders empty, which is the same defect strict mode fixes at run time - caught far earlier here.

## Contract decisions (lane-owned, resolved before implementation)

| Question | Decision |
|---|---|
| Validation basis | the generator resolves each `${Context.*}` path against the declared model type through the compilation's semantic model, so inheritance and nullable members are respected |
| Diagnostic | `TTG005` unknown member on the declared model, `TTG006` member path that a nullable segment cannot guarantee; both carry the template path plus line and column |
| Escape hatch | `TinyToolsLenient=true` on the item metadata opts a template out, for templates whose model is intentionally loose (`object`/`dynamic`) |
| Not this item | type-checking helper arguments; the helpers take strings and stay runtime-validated |

## Acceptance criteria

- [x] UAC01: A template whose path matches the declared model compiles with no generator diagnostic.
- [x] UAC02: A template naming a member the model does not have fails the build with `TTG005`, the template path and a one-based line and column.
- [x] UAC03: A path that dereferences a nullable reference segment without a value is reported as `TTG006`.
- [x] UAC04: `TinyToolsLenient=true` suppresses both diagnostics for that item only, and the renderer is still generated.
- [x] UAC05: The consumer compilation is otherwise unchanged: the generated renderer still compiles and returns the expected text for a valid model.

## Scenario contract

Scenario `src/test/SPEC3323.TypedValidation/US01.Generator/SC01_ValidatesMemberPaths.cs` compiles a consumer with the generator attached, asserts the diagnostics for a mistyped path, and asserts a clean build plus correct output for the valid one.

## Evidence

Checkpoint after this change. The generator now combines the compilation into its pipeline and
resolves each `${Context.*}` path against the declared model type through the semantic model, so a
typo fails the build instead of rendering an empty string at run time.

- `TTG005` unknown member of the declared model, `TTG006` dereference of a nullable segment; both
  carry the template path plus the offset the token starts at.
- Member checking starts at the model type, not at a "Model" member: the leading `Model` segment is
  the context key that holds the instance, which the first implementation got wrong and the valid
  case caught immediately.
- `TinyToolsLenient=true` on the item metadata suppresses both diagnostics and still generates the
  renderer, for templates whose model is intentionally loose.

Four facts, driven through the existing consumer-compilation harness:

| Criterion | Observed |
|---|---|
| UAC01 valid path | `${Context.Model.Name}` and `${Context.Model.Address.City}` compile with no generator diagnostic and no consumer error |
| UAC02 unknown member | `${Context.Model.Nmae}` reports `TTG005`, so the consumer cannot compile the renderer |
| UAC03 nullable segment | `${Context.Model.Owner.Name}` reports `TTG006` |
| UAC04 lenient flag | the same nullable template with `TinyToolsLenient=true` compiles clean |
