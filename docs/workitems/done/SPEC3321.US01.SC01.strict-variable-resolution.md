## Outcome

A template rendered in strict mode refuses an unknown variable instead of emitting an empty string.

## Problem

A missing context key currently logs a warning and resolves to `""`, so `Hello ${Name}` renders `Hello ` and the caller ships plausible but wrong output. For a tool whose value is deterministic generation, a silent empty string is the worst failure mode.

## Contract decisions (lane-owned, resolved before implementation)

| Question | Decision |
|---|---|
| Opt-in or default | opt-in through `TemplateRenderOptions { StrictVariables = true }`; the default stays lenient so existing templates keep rendering |
| Failure surface | `TemplateResolutionException` naming the expression, the missing segment and its line/column, derived from the same locating logic `ValidateSyntax` already uses |
| Scope | unknown context keys and unknown pipe helpers both fail; a known key with a null value still renders empty unless `FailOnNull` is set |
| Diagnostic parity | the exception carries a stable code (`TR001` unknown key, `TR002` unknown helper) so a host can report it without parsing text |

## Acceptance criteria

- [x] UAC01: A missing key under strict mode raises `TemplateResolutionException` naming the expression and the missing segment, and no output is produced.
- [x] UAC02: The same template under the default mode still renders, with the unknown segment resolving to an empty string.
- [x] UAC03: An unknown pipe helper under strict mode raises the exception with code `TR002`; under the default mode the value passes through unchanged.
- [x] UAC04: A known key holding null renders empty under strict mode unless `FailOnNull` is set, in which case it raises with code `TR003`.
- [x] UAC05: The exception reports a one-based line and column that point at the offending `${...}` token.
- [x] UAC06: Existing behavior scenarios keep passing with strict mode off, proving the default is unchanged.

## Scenario contract

Scenario `src/test/SPEC3321.Strict/US01.UnknownVariables/SC01_RefusesUnknownVariables.cs` renders the same template twice, once per mode, and asserts the captured exception code, message, line and column alongside the lenient output.

## Evidence

Checkpoint after this change. Strict rendering is an explicit policy on the engine, validated
before any output exists.

- `TemplateRenderOptions` carries `StrictVariables` and `FailOnNull`; `TemplateRenderOptions.Lenient`
  is the default and `Strict` sets both. `TinyTemplateEngine.Render(template, context, options)`
  validates every `${...}` token first and only then renders, so a refusal never leaves partial text.
- `TemplateResolutionException` carries a stable `Code`, one-based `Line` and `Column`:
  `TR001` unknown context key, `TR002` unknown pipe helper, `TR003` a known key that resolved to null
  while `FailOnNull` is set.
- `ExecutionContext.Has(key)` distinguishes "not set" from "set to null", which the old `Get` could
  not, and that distinction is the whole reason `TR003` can exist.

Eight facts, all captured through the public `Render`:

| Criterion | Observed |
|---|---|
| UAC01 unknown key | `TR001` at line 1 column 7 naming `Missing` |
| UAC02 lenient default | `Hello !` - the default still renders exactly as before |
| UAC03 unknown helper | `TR002` naming `nosuchhelper` |
| UAC07 lenient helper | `Ada` - an unknown helper still passes the value through |
| UAC04 null refusal | `TR003` naming `Alias` |
| UAC08 null allowed | empty text when `FailOnNull` is off |
