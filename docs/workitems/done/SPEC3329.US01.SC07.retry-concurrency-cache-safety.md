## Outcome

A client that retries a create does not create twice, a concurrent update is rejected rather than lost, and a cached read never serves another caller's data.

## Problem

Create has no idempotency story and update overwrites whatever it finds, which are the two ways a template library silently loses work.

## Acceptance criteria

- [x] UAC01: A create answers 201 and stores one resource.
- [x] UAC02: Repeating the create with the same idempotency key returns the same resource instead of a second one.
- [x] UAC03: The replay answers 200, so a client can tell a replay from a creation.
- [x] UAC04: Reusing the key with a different payload answers 409 instead of silently creating something else.
- [x] UAC05: The key refusal carries a stable problem type.
- [x] UAC06: A read names the current state with an ETag.
- [x] UAC07: A template response is declared uncacheable, because the data belongs to one deployment's credential.
- [x] UAC08: An update carrying a stale ETag is refused with 412 instead of overwriting the newer write.
- [x] UAC09: An update carrying the current ETag is accepted.

## Scenario contract

Given two clients, an empty isolated database and a fixed clock, When create keys/payloads are replayed, two updates use the same entity tag, and reads follow each write, Then the results are `IdempotentReplay`, `StaleWriteRejected`, and `CacheReflectsCommittedState` with row counts, response IDs/statuses, ETags and snapshots. Keep requests and observed reads visible in `SC07_ProtectRetriesAndConcurrency.cs`; one Fact per UAC01-UAC03.

## Divergence from the backend scope

The backend surface is `/api/plugins/{**path}` behind an account, device and IP model owned by the Auth
lane. Tinytools has one credential and seven template operations, and it deliberately refuses plugin
paths (`SPEC3315-US02-SC02`). Where the backend criterion depends on accounts or devices, this scope
requires the equivalent on this surface - credential scoping, provenance of the configured key, and
untrusted client headers - rather than inventing an account system here.

Observed: a create answers 201; the same `Idempotency-Key` with the same payload answers 200 with the
original id; the same key with a different payload answers 409 with the `idempotency-key-reused`
problem type; a read declares `ETag` and `Cache-Control: no-store`; a stale `If-Match` answers 412;
the current `If-Match` answers 200.

### What changed

- `IdempotencyStore` remembers a create by its key for **24 hours**, bounded to 512 entries. A retry
  inside the window replays the original resource; the same key with a different payload is refused
  rather than silently creating a second template.
- A read now answers an `ETag` computed from the response it would return, and an update compares
  `If-Match` against the stored state and answers `412` when it differs. The precondition is read with
  `AsNoTracking`, because the update attaches its own instance of the same row and a tracked copy
  makes EF refuse the second one - that was a 500 until the read stopped tracking.
- Every template response declares `no-store`, which is the honest policy: the data belongs to one
  deployment's credential and a shared cache must never hold it.

### Retention, chosen

24 hours, recorded here because it is a product number rather than a technical constant: long enough
for a client's retry window and short enough that the store does not become a request archive.
