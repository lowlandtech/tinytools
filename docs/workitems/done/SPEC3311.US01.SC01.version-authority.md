## Outcome

One declared version produces the package version, the git tag, the readme badge and every feed version, so no release can carry a version that disagrees with its tag.

## Acceptance criteria

- [x] UAC01: Exactly one place declares the version, and every other surface derives from it or is explicitly documented as derived.
- [x] UAC02: The tag, project version, readme badge and published feed entries agree for the next release.
- [x] UAC03: No workflow can produce a version outside that scheme, including the stale unpadded CalVer variants recorded in `src/lib/obj/Release`.
- [x] UAC04: Evidence records the resolved version at pack time and the corresponding feed entries.

## Scenario contract

No product behavior to test. Evidence is the pack log with the resolved version, the tag, the readme badge text and the feed listing, captured for one release candidate.

## Refinement gaps

- The owner must choose the scheme (tag-driven `Version` with `-p:Version` from the tag, or CI CalVer) and the feeds that remain authoritative, because the choice defines the tag and workflow contract. The badge is also maintained by hand today and needs a stated rule.

## Scheme decision (lane-owned, resolved before implementation)

**Chosen: `Directory.Build.props` is the authority, and the tag derives from it.**

Why not the alternative (tag-driven `-p:Version`): that is what the repository did, and it is
exactly how `LowlandTech.TinyTools` reached `2026.5.31` while `.Core` and `.Frontend` sat on
`2026.10.1`, and how the readme badge froze at `2026.5.29`. A tag-derived version can only be
correct in CI; every local `dotnet pack` silently disagrees. Declaring the version once and
having the tag checked against it makes the local pack, the CI pack, the badge and the tag the
same number by construction.

| Surface | How it derives |
|---|---|
| package version | MSBuild reads `<Version>` from `Directory.Build.props`; no workflow passes `-p:Version` or `-p:PackageVersion` any more |
| release tag | `v<version>`; `tags.yml` resolves the declared version with `dotnet msbuild -getProperty:Version` and **fails** when the tag disagrees |
| readme badge | rewritten by `eng/set-version.ps1`, which changes the props file and the badge together |
| changelog | the release heading must be `# <version>`; the script warns when it is missing |
| feed entries | follow the packed version, which is now the declared one |

`eng/set-version.ps1 -Version <x>` is the single release command. Stale CalVer variants under
`src/lib/obj/Release` are untracked build output (`git ls-files 'src/lib/obj'` is empty), so
they cannot leak into a package now that nothing passes a version on the command line.

## Evidence

- `Directory.Build.props` declares `<Version>2026.10.3</Version>`; `<Version>` was removed from
