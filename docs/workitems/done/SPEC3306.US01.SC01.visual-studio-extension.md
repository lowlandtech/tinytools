## Outcome

Authors get template diagnostics, completion and a live preview inside the editor they already
use, because the capability lives in a language server rather than in one editor's extension model.

## Scope change (user decision, 2026-10-31)

This item was "Build a Visual Studio template editing extension". The user chose the editor-agnostic
delivery and keeps the packaged VSIX as a separate, gated item (M4-010).

The measurement behind that decision:

| Finding | Consequence |
|---|---|
| the local Visual Studio is **18** Professional and the newest published SDK is **17.14** | a VSIX built here would target VS 17 and would not load in VS 18 |
| the repository has no Visual Studio test host, and the refinement forbids putting editor calls in the library test project | nothing could verify an extension automatically |
| a VSIX project in `tinytools.slnx` would break every CI leg | the pipeline that went green today would go red again |
| packaging a VSIX **is** possible here (`net472` + `Microsoft.VSSDK.BuildTools` produced a container with no Visual Studio installed) | the blocker is verification and targeting, not tooling |

The language server already delivers the four capabilities the original acceptance named, and it is
verifiable end to end, so the item delivers through it.

## Acceptance criteria

- [x] UAC01: The server advertises text document sync, completion with `$` and `.` triggers, and the `tinytools.preview` command during `initialize`.
- [x] UAC02: A malformed template publishes a diagnostic carrying the engine's code and position, and the message names the problem.
- [x] UAC03: Completion without a trigger character returns the pipe helpers; with the `.` trigger it returns the declared model members.
- [x] UAC04: The preview command renders the open document for the requested revision and reports whether the request was stale.
- [x] UAC05: A malformed command is answered with a JSON-RPC error and the server keeps serving; it does not exit.
- [x] UAC06: Editor setup for both editors is documented in a published guide, and the session check that backs it is committed.

## Scenario contract

`src/test/SPEC3324/...` covers the server's behaviour through its use case. The end-to-end contract
is `eng/lsp-session-check.py`, which spawns the built server and speaks LSP over stdio, because the
editor contract is a process contract that no in-process test can prove.

### What this item deliberately does not deliver

A packaged `.vsix`. It is M4-010 (`SPEC3306-US01-SC02`), which records the packaging recipe that was
proven here and the exact prerequisite: a Visual Studio SDK that matches the release the extension
would target.
