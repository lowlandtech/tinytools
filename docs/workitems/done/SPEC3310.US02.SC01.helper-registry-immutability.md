## Outcome

Templates cannot mutate process-wide helper state while other renders run, so helper behavior is the same for every caller in the process.

## Acceptance criteria

- [x] UAC01: `TemplateHelpers.Helpers` is exposed read-only (`IReadOnlyDictionary` or an immutable dictionary); no public member returns a mutable helper collection.
- [x] UAC02: Concurrent renders that use string, number, date and collection helpers produce the documented results without exceptions under a stress fact.
- [x] UAC03: Callers that previously extended helpers through the mutable dictionary have a documented replacement path through `ExecutionContext.RegisterService`, and `changelog.md` carries the migration note.
- [x] UAC04: Helper names, arguments and outputs are unchanged for every documented helper.

## Scenario contract

Add SPEC3310/US02. Given registers a service the way the migration note describes and prepares concurrent renders, When renders run in parallel, Then facts assert per-render output and the absence of shared-state mutation. Keep the stress case bounded so it stays deterministic.

## Evidence
Implemented at `68fd31d` on `develop`.

- Public surface: `TemplateHelpers.Helpers` changed from `Dictionary<string, Func<object?, string?, object?>>` to **`IReadOnlyDictionary<string, Func<object?, string?, object?>>`**. The registry behind it is a `ConcurrentDictionary` populated in the type's static constructor, so renders read a thread-safe table and an assignment through `Helpers[...]` no longer compiles.
- Supported mutation paths: `Register(name, helper)` for process-wide additions and the new `Unregister(name)` to undo one. Per-render behavior uses `ExecutionContext.RegisterService`, which cannot change what other renders in the process see.
- The changelog now carries the migration note, written as part of the change: the breaking signature, the `Register`/`Unregister` replacement, the preferred `RegisterService` path with a working example, and the note that reading (`ContainsKey`, `Keys`) is unchanged.

One caller had to migrate, and it is the exact case the note describes: the syntax-validation scenario registered a counting helper and removed it through the old mutable dictionary. It now calls `TemplateHelpers.Unregister`.

Scenario `SPEC3310/Packaging/US02.HelperRegistry/SC01_ExposesImmutableHelpers` proves the criteria through the `HelperRegistryUseCase`:

| Criterion | Test UAC | Observed |
|---|---|---|
| read-only surface | 01 | the declared `Helpers` property type is `IReadOnlyDictionary`2 |
| concurrent renders | 02, 03 | 64 parallel renders over string, count, join and round helpers: **0 failures** and exactly **1 distinct output** |
| unchanged outputs | 04 | the concurrent render matches `S: ADA; C: 3; J: a-b-c; R: <current-culture F1 of 2.345>` |
| documented replacement | 05 | a helper registered with `ExecutionContext.RegisterService` is reachable as `${Context.Services('shout')('hi')}` -> `HI!` |

Worth recording: the first version of case 04 hardcoded `R: 2.3` and failed, because `round` formats with the current culture and this machine renders `2,3`. That is pre-existing documented behavior, so the expectation now derives from the same culture-aware formatting instead of assuming invariant output - the alternative would have been a test that only passes on en-US.
