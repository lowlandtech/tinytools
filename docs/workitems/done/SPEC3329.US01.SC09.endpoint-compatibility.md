## Outcome

A consumer pinned to a published version keeps working across additive changes, and a breaking change is either versioned or has a recorded consumer migration.

## Problem

The app reads the same contract the API exposes, so a breaking change today silently breaks the first consumer rather than a version negotiation.

## Acceptance criteria

- [x] UAC01: Version 1 is the default contract; a call with no version header is served.
- [x] UAC02: An explicit `api-version: 1` is the same contract, not a different behaviour.
- [x] UAC03: An unsupported version is refused with 400 rather than silently served as version 1.
- [x] UAC04: The version refusal carries a stable problem type, like every other refusal.
- [x] UAC05: A malformed version is refused the same way, so a typo cannot select a contract.
- [x] UAC06: The pinned consumer in this repository reads the running host and gets its data.
- [x] UAC07: An additive field in a response stays consumable.
- [x] UAC08: A breaking shape - a resource without its identifier - is detected rather than accepted silently.

## Scenario contract

Given the published v1 document and the three in-repository consumers, When each consumer calls the host with omitted, v1, malformed and unsupported version headers and the additive/breaking fixtures are compared, Then the named results are `VersionOneAccepted`, `UnsupportedVersionRejected`, `ConsumersRemainCompatible`, and `BreakingChangeRequiresMigration` with statuses, operation names and diff paths. Keep setup and calls visible in `SC09_PreservesApiCompatibility.cs`; use a distinct Fact for each stable UAC.

## Divergence from the backend scope

The backend surface is `/api/plugins/{**path}` behind an account, device and IP model owned by the Auth
lane. Tinytools has one credential and seven template operations, and it deliberately refuses plugin
paths (`SPEC3315-US02-SC02`). Where the backend criterion depends on accounts or devices, this scope
requires the equivalent on this surface - credential scoping, provenance of the configured key, and
untrusted client headers - rather than inventing an account system here.

### What changed

The host served one unversioned contract and had no way to answer a caller who asked for another:
any header value was ignored, so a client that pinned a version had no signal. `ApiVersionMiddleware`
reads `api-version`, serves version 1 when it is absent or `1`, and refuses anything else with the
same problem document shape as every other refusal, before authorization runs. It reads one header
and changes nothing else, so a version cannot quietly alter an operation's behaviour.

### Scope, stated plainly

UAC06 exercises **one** pinned consumer - the frontend client the package ships - not the CLI or
the app store, which are not separate HTTP clients today. The compatibility fixture checks the
consumer contract at the JSON level (additive tolerated, missing identifier detected); it does not
deserialize into the entity type, because a missing `id` is a default `Guid` there rather than a
failure. That is recorded as the honest limit of the check rather than glossed.
