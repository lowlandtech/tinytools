## Outcome

A single edit renders once. The watcher reports a change only after the file's stamp has stayed
unchanged for a settle window of its own, so a write that is still in progress - including one that pauses
part-way - is not rendered. The limit of that promise is measured and stated, not glossed.

## What was wrong — the incident

`SPEC3306-US03-SC01` UAC03 promises "one render per relevant change", but `TemplateWatcher` reported every
stamp it observed:

```csharp
if (stamp != _stamps[file]) { _stamps[file] = stamp; changed.Add(file); }
```

Writing a file is not one operation: it is truncated, then filled. CI run `44759369081` on
`windows-latest` failed with

```
Expected useCase.Cases["WatchRevisions"] to be 1, but found 2.
  SC02_WatchesRelevantFiles.UAC03_ReRendersOnRelevantChange
```

and the rerun of the same run was green - a timing-dependent double count. The acceptance was right.

## First attempt, and why it was returned

The first fix reported a change once its stamp had been seen **twice in a row** (`2026.10.7`). It made the
acceptance stop flaking - ten consecutive local runs, 953/953 suite - and I recorded it as "one edit renders
once, and a half-written template never renders". That was an overclaim, and a packaged-consumer smoke
falsified it:

| Package | staged write, 120 ms pause |
|---|---|
| `2026.10.7` (first fix) | **2, 2, 2** |
| `2026.10.6` (before) | **2, 2, 2** |

One quiet poll is only as long as the poll interval, so a write pausing longer settled twice and rendered
twice - and the half-written file rendered first. Coordinator-1 agreed and returned the item to `doing`
with the evidence preserved.

## The guarantee that now holds

A change is reported once its stamp has stayed unchanged for `settle`, a duration of its own, 250 ms by
default and **independent of the poll interval**:

```csharp
if (_unsettled.TryGetValue(file, out var pending) && pending.Stamp == stamp)
{
    if (now - pending.Since < Settle) { continue; }
    _stamps[file] = stamp; _unsettled.Remove(file); changed.Add(file);
}
else { _unsettled[file] = (stamp, now); }
```

`Settle` is exposed on the watcher, because the honest boundary is the consumer's business: a write that
pauses longer than the window is, in the only sense polling can observe, more than one change.

Run against `LowlandTech.TinyTools 2026.10.8` from the workspace feed, not against the source tree:

## Cost

The first render after an edit now waits for the settle window: about 250 ms at the CLI defaults, versus one
poll interval before. That is the price of not rendering a file that is still being written.

## Acceptance criteria

- [x] UAC01: A single write and an edit that pauses inside the settle window each render exactly once, measured on the published package.
- [x] UAC02: A file whose stamp has not yet settled is not reported, so a write in progress is not rendered.
- [x] UAC03: An unrelated file change renders zero times and the watched set is unchanged.
- [x] UAC04: A write that pauses past the settle window renders more than once, and that boundary is measured and stated rather than hidden.
- [x] UAC05: The behaviour rides a published version with recorded digests, and the versions published before it are untouched.
