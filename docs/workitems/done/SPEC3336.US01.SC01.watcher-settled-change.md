## Outcome

The watcher renders once per edit, which is what `SPEC3306-US03-SC01` UAC03 already promised ("one render
per relevant change"), and the Windows acceptance that kept failing on the count stops failing.

## What was wrong

`TemplateWatcher` compared file stamps and reported **every** change it saw:

```csharp
if (stamp != _stamps[file]) { _stamps[file] = stamp; changed.Add(file); }
```

Writing a file is not one operation. It is truncated and then filled, so one edit can present two (or
more) distinct stamps to a poller. At the 20 ms interval the acceptance uses, both were observed, so a
single edit rendered twice.

The acceptance is what caught it: CI run `44759369081` on `windows-latest` failed with

```
Expected useCase.Cases["WatchRevisions"] to be 1, but found 2.
  SC02_WatchesRelevantFiles.UAC03_ReRendersOnRelevantChange
```

and the rerun was green, which is the signature of a timing-dependent double count rather than a broken
feature. The test was right; the product was not.

## Change

A change is reported only once its stamp has been observed **twice in a row**:

```csharp
if (_unsettled.TryGetValue(file, out var seen) && seen == stamp)
{
    _stamps[file] = stamp; _unsettled.Remove(file); changed.Add(file);
}
else { _unsettled[file] = stamp; }
```

A file whose stamp stops changing is settled; a file still being written is not. Two consequences, both
intended: one edit renders once, and a half-written template is never rendered.

Cost: the first render after an edit now takes one extra poll interval (about 250 ms at the CLI default,
40 ms at the acceptance's 20 ms). No documentation promised a tighter latency; the mechanism was already
documented as timestamp polling with a documented interval.
