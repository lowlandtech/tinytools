## Outcome

Consumers can rely on one casing, one identifier and timestamp convention, one collection shape and one failure shape, so a client does not need special cases per endpoint.

## Problem

Responses are built ad hoc from entities and a render body echoes whatever it was given; there is no recorded convention to keep them consistent as the surface grows.

## Acceptance criteria

- [x] UAC01: A template response uses one casing - camelCase - for every member.
- [x] UAC02: A list answers one collection shape: a JSON array, not a wrapper that changes per endpoint.
- [x] UAC03: A create names the created resource in its Location header.
- [x] UAC04: A delete answers a bodyless 204.
- [x] UAC05: A refusal answers `application/problem+json`.
- [x] UAC06: The problem document's status matches the HTTP status.
- [x] UAC07: The problem document carries a stable type identifier.
- [x] UAC08: The problem document carries a trace identifier.
- [x] UAC09: A malformed body stays a caller error (400), not a server error.
- [x] UAC10: A malformed body answers the same problem media type as any other refusal.

## Scenario contract

Given the seven mapped operations and concrete DTO instances from `TemplateContracts`, When success, missing-resource, malformed-body and authorization responses are captured from a real host, Then the named results are `WireShape`, `StatusAndOrdering`, and `ProblemContract` with JSON keys, GUID shape, content type, headers, body presence, ordering and secret-redaction observations. Keep the Given/When visible in `SC06_UsesConventionalResponses.cs`; one Fact per UAC01-UAC03.

## Divergence from the backend scope

The backend surface is `/api/plugins/{**path}` behind an account, device and IP model owned by the Auth
lane. Tinytools has one credential and seven template operations, and it deliberately refuses plugin
paths (`SPEC3315-US02-SC02`). Where the backend criterion depends on accounts or devices, this scope
requires the equivalent on this surface - credential scoping, provenance of the configured key, and
untrusted client headers - rather than inventing an account system here.

Observed: the template response carries exactly `id,name,isActive,versions,packages`; a list is a JSON
array; a create answers `201` with `Location: /api/templates/{id}`; a delete answers `204` with a
zero-length body; an absent key answers `application/problem+json` with `status` 401, a stable
`type` and a `traceId`; a malformed body answers `400` with the same media type.

### What changed

The two refusal paths answered a bare `{ "error": "..." }` object - one from the authorization
result handler, one from the malformed-body handler. Both now answer RFC 9457 problem documents
through `ApiProblems`, which owns the media type, the stable type identifiers
(`api-key-required`, `api-key-rejected`, `malformed-body`), the instance path and the trace
identifier. A client parses one error contract instead of one per endpoint.

### Declared absence

The contract carries no timestamp members today, so the "UTC timestamp" clause has nothing to
assert. That is recorded rather than invented: adding timestamps is a contract change, not a
convention, and no scope asks for it.
