## Outcome

Callers can explicitly validate supported engine-template syntax before rendering through `ITemplateEngine.ValidateSyntax(string)`, receiving a `TemplateSyntaxValidationResult` that distinguishes valid input from syntax failure without reusing the existing example-output `TemplateValidationResult`.

## Acceptance criteria

- [x] UAC01: Valid supported control-flow and interpolation syntax returns `TemplateSyntaxValidationResult.IsValid == true` with no diagnostics and retains the existing render output.
- [x] UAC02: Malformed control-flow or interpolation syntax returns `IsValid == false` with at least one stable diagnostic code and message; source coordinates are added by dependent scope SPEC3300-US08-SC01.
- [x] UAC03: Validation is an explicit parse/validate operation; it does not invoke render helpers or change render behavior implicitly.
- [x] UAC04: The existing `TemplateValidationResult` for comparing example output remains unchanged and distinct from syntax validation.

## Scenario contract

Create US04 for engine-level validation, separate from the existing `ITemplate.Validate` example-output contract. Add `ValidateSyntax(string)` to `ITemplateEngine` and a `TemplateSyntaxValidationResult` with `IsValid` and diagnostics containing stable code/message fields; reserve line/column semantics for dependent M2-003. Tests should verify validation only and should not make malformed `Render` behavior an implicit API contract.

## Delivery evidence

Implemented at `1781008` on `develop`.

- `TemplateSyntaxValidationResult` (`src/lib/Core/TemplateSyntaxValidationResult.cs`) carries `IsValid` plus an ordered list of `TemplateSyntaxDiagnostic(Code, Message)`, with a `Valid` singleton and a `Codes` projection. It is a separate type from `TemplateValidationResult`, which still belongs to `ITemplate` example-output comparison and is untouched.
- `ITemplateEngine.ValidateSyntax(string)` is the explicit parse/validate operation; `TinyTemplateEngine` implements it without calling `Render`, `ProcessControlFlow`, `ResolveString` or any helper.
- Stable diagnostics: `TS001` unterminated `${` interpolation, `TS002` unterminated `@*` comment, `TS003` `@if`/`@foreach` without a condition, `TS004` control-flow statement without an opening brace, `TS005` control-flow block that is never closed. Block closure uses the same line/brace counting the renderer uses, so validation and rendering agree on where a block ends. Source coordinates stay out of scope for `SPEC3300-US08-SC01`/`M2-003`.

Scenario `SPEC3302/US01.../US04.PreRender/SC01_ValidatesTemplateSyntax` captures nine cases through the `PreRenderValidationUseCase`:

| Test UAC | Case | Observed |
|---|---|---|
| 01 | supported template with interpolation, `@if` and `@foreach` | `IsValid` true |
| 02 | a plain render still produces the previous output | `Hello Ada` |
| 03 | `Hello ${Name` | `TS001` only |
| 04 | `Hello @* never closed` | `TS002` only |
| 05 | `@if {` | `TS003` only |
| 06 | `@if (...) {` never closed | `TS005` only |
| 07 | `${Name \| scratchcount}` | `IsValid` true - syntax is fine even though the helper is not run |
| 08 | the counting helper invoked by validation | 0 calls |
| 09 | an `ITemplate` example result | still `TemplateValidationResult` |

Cases 07 and 08 are the behavioural proof for UAC03: a registered helper that increments a counter is never invoked by validation, and the scenario removes it again so the shared registry is left as found.

## Refinement evidence

The current `TemplateValidationResult` is defined in `src/lib/Templates/ITemplate.cs` and represents expected-output comparison for `ITemplate`; there is no engine syntax-validation API yet. This item establishes a distinct `TemplateSyntaxValidationResult` and explicit `ITemplateEngine.ValidateSyntax` contract. `SPEC3300-US08-SC01` depends on this scope to add diagnostic coordinates; malformed `Render` output is not defined by this validation feature.
