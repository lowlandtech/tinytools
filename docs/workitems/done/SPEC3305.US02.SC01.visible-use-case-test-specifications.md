## Outcome

Every existing Tinytools test case is represented by a discoverable test specification with a story-level UseCase and named case result, while each scenario keeps its Given and When implementation visible as a practical example of using the library's public API.

## Acceptance criteria

- [x] UAC01: A complete inventory maps every active test case under `src/test` to a stable specification, user story, scenario and named result case; the before/after discovered case counts reconcile with no silent omissions.
- [x] UAC02: Each story has an explicit UseCase and typed/cased result model whose named outcomes make the tested success, refusal/failure, boundary or recovery behavior clear.
- [x] UAC03: Given setup remains visible in the scenario source, including construction/configuration through the public Tinytools API; it is not hidden in a UseCase, fixture or opaque helper.
- [x] UAC04: When action remains visible in the scenario source and directly shows the public operation under test; it is not moved into a UseCase or hidden behind an invocation helper.
- [x] UAC05: Each behavior case has its own stable, discoverable assertion identity and checks an observed result; no expected-value-only, placeholder, skipped or empty case counts as coverage.
- [x] UAC06: Existing meaningful behavior coverage and public-usage examples are preserved or increased; any removed/obsolete case has a cited reason and replacement coverage in the inventory.
- [x] UAC07: The migrated suite passes on `net8.0`, `net9.0` and `net10.0`, and the scoped test-spec/layout checks report the complete selected inventory with no unexplained skips.

## Scenario contract

Treat each test as executable documentation. A story UseCase names the caller's goal and defines the result/case vocabulary; scenario Given and When remain ordinary, readable test code and show the actual Tinytools setup and operation. Then/case assertions consume captured results. Use the repository's xUnit and FluentAssertions conventions unless a specific limitation is recorded with a compatible alternative. Split oversized scenarios by behavior without changing existing SPEC/US/SC identities unnecessarily.

### Migration approach for the remaining bulk

The remaining `SPEC3300` violations are dominated by three heterogeneous files (`US02.ControlFlow/SC01` 226, `US06.StressAndEdgeCases/SC01` 118, `US01/SC10`-`SC12` ~150) whose Facts each arrange and act inside the Fact body. Two options were considered:

- one file per Fact, which multiplies the file count into the hundreds and forces speculative `SPEC/US/SC` identity churn the workitem warns against;
- one scenario whose `Given` prepares every input and whose `When` performs the same public operation once per case, capturing each result, with one single-line Fact asserting one captured result.

The second is chosen for the heterogeneous files because it keeps the existing `SPEC/US/SC` identities, keeps the operation visible and executed in `When`, and satisfies one-observed-result-per-Fact without inventing identities. Where a file's cases use genuinely different operations, it will be split along those operations instead. `SPEC3303` stays untouched while `coordinator-1` owns #45.

Three pattern findings are worth recording because they are not obvious:

- xunit re-instantiates a scenario per Fact while the fixture is shared, so a Fact can never read a Given instance field. Identity comparisons had to travel through the UseCase cases (`BeSameAs(useCase.Cases["That"])`).
- Exception cases capture the deferred delegate, not the exception, because storing the exception forces `.BeOfType<T>()` and loses `.Throw<T>()`'s derived-type semantics (`ArgumentNullException : ArgumentException`).
- `Cases` is `object?`, so captured collections and strings are cast to their known type in the Fact; `Be(true)`/`Be(false)` replaces `BeTrue()`/`BeFalse()` on boxed booleans.
- One assertion shape genuinely changed: `US02/SC12`'s `Assert.Throws<...>().Message.Should().Contain(a).And.Contain(b)` became a wildcard `.WithMessage("*...*...*")` because a second `.Should(` breaches the one-assertion rule. Same exception type, both fragments still asserted, but wildcard matching is ordered where the two `Contains` were not. Disclosed rather than hidden.
