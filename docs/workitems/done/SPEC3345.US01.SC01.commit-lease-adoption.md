## Outcome

Every checkpoint this lane makes goes through `eng/git-commit-lease.ps1`, so a stage, commit and push can
no longer interleave with another worker's index. The lane's own history up to this point was made with raw
`git add`/`commit`/`push`, which the shared `agentic-git` skill forbids.

## The defect this corrects

The workspace gained an `agentic-git` skill with a hard boundary:

> Do not directly run mutating Git commands such as `add`, `commit`, `push` … outside those tools.

Every checkpoint this lane has made was made exactly that way. It happened to work — the tree was clean each
time and the pushes were clean fast-forwards — but that is luck, not safety: a lease exists to stop two
workers staging into one index, and raw `git add` has no way to notice that another owner holds it.

The failure this lane already suffered once is the same class: an `git add -A` swept a concurrent runner's
uncommitted work into commit `5f7ac27` and misattributed it. The lease tool refuses that by construction,
because it stages only an explicit path list and verifies the staged set before committing.

## What was verified before adopting

The tool was probed rather than trusted:

```
pwsh eng/git-commit-lease.ps1 -RepositoryRoot <repo> -Owner tinytools `
     -Scope SPEC3344-US01-SC01 -Paths ".chatbox" -Message "test(probe): no-issue"
-> "Staged path set differs from this workitem; index preserved:"
   exit 1
```

That is the correct behaviour: it refused a path set that did not match a real dirty tree, and it preserved
the index rather than unstaging. So the tool is live and enforcing, not a no-op wrapper.

This checkpoint was then made with the same tool and this workitem's own scope, which is the proof that
matters — the mechanism is adopted, not merely described.

## What changes in practice

| Before | After |
|---|---|
| `git add <paths>` then `git commit` then `git push` | one `eng/git-commit-lease.ps1` invocation |
| index contention invisible | the tool refuses while another owner's changes are staged |
| `git add -A` could absorb foreign work | only the explicit `-Paths` list is staged, and the staged set is verified |
| commit message free-form | `type(scope): SCOPE-ID #issue` in the subject, detail in the body |

The commit subject convention also changes: the source scope ID and managed issue number go in the subject,
and the behavioural summary moves to the body — which is what the skill requires and what this lane had been
doing in the opposite arrangement.

## What this does not change

- The lane stays on `develop`; no branch or worktree is created. `gitflow` worktree mode is explicitly not
  implemented yet, so nothing here imitates it.
- Ownership, source lifecycle, board, mirror and the managed issue are untouched.
- Historical commits are not rewritten. The lane's earlier raw-Git checkpoints stay as they are; this scope
  fixes the practice from here on and records the reason.
