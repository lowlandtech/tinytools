## Outcome

Each of the seven template operations answers a real request with the declared status, a shape a consumer can deserialise, and the state change it promises - and a reader can see which endpoint is proven by which check.

## Problem

The endpoints exist and are exercised piecemeal by the app and store specs, but no pass proves them as an endpoint surface: status codes, boundaries and state effects are asserted incidentally, and nothing says which operation has no evidence at all.

## Acceptance criteria

- [x] UAC01: A list request against a real host answers 200.
- [x] UAC02: A create request answers 201.
- [x] UAC03: The created body carries an identifier and its versions.
- [x] UAC04: A read returns the name that was stored.
- [x] UAC05: An update changes the name in place.
- [x] UAC06: Render returns the engine's output for the submitted template.
- [x] UAC07: Validation reports the version valid.
- [x] UAC08: An unknown identifier answers 404 for a read, a write and a delete.
- [x] UAC09: A malformed body answers 400 rather than 500.
- [x] UAC10: A delete answers 204 and the template is gone afterwards.
- [x] UAC11: All seven operations succeed inside one executed scenario.

## Scenario contract

Given an isolated host per operation, when each declared request runs, then the status, the body shape and the stored state are observed, and every operation appears in the coverage map.

The scenarios live under `src/test/SPEC3329.EndpointProtection/US01.EndpointProtection/` and follow the
shared Agentic Gherkin grammar: one scenario class per file, Given construction and When calls visible in
the scenario source, one `[Trait("UAC", "NN"), Fact]` per single-line assertion, and a unique UAC per file.

## Divergence from the backend scope

The backend surface is `/api/plugins/{**path}` behind an account, device and IP model owned by the Auth
lane. Tinytools has one credential and seven template operations, and it deliberately refuses plugin
paths (`SPEC3315-US02-SC02`). Where the backend criterion depends on accounts or devices, this scope
requires the equivalent on this surface - credential scoping, provenance of the configured key, and
untrusted client headers - rather than inventing an account system here.

### Two defects this scope found and fixed

Both were answered with **500**, which tells a caller the server broke when the caller was wrong:

| Case | Before | Cause | Fix |
|---|---|---|---|
| `PUT /api/templates/{unknown}` | 500 | marking a detached row `Modified` makes EF throw `DbUpdateConcurrencyException` on save, and the endpoint cannot turn that into 404 | `TemplateService.UpdateAsync` checks existence first and returns `null`, which the endpoint already maps to 404 |
| `POST` with a malformed body | 500 | `UseExceptionHandler` turned the binder's `BadHttpRequestException` into a server error | `MalformedRequestExceptionHandler` returns the exception's own status with a problem body |

Both were delivered by M6-002 and are repaired here, under the scope that proves endpoint
boundaries. Recorded on #68 as a follow-up defect note.

### Where these run

Locally with the workspace feed present: `-p:HostSpecs` defaults to `true` and the scenarios compile
against the API host. CI sets `HostSpecs=false`, which drops that host reference, so
`SPEC3329.EndpointProtection` joins the three host folders in the removal group of
`LowlandTech.TinyTools.Tests.csproj` and the matrix still runs 953 specs.

That was a correction, not a plan: the first push compiled here and failed on all three operating
systems (run `41165642885`) because the scenarios referenced `TemplateApiFactory`, which lives in
`SPEC3315.Server` - a folder CI excludes. The honest fix is to declare the dependency instead of
duplicating the factory, and the csproj comment now says why the folder is excluded.
