## Outcome

A caller cannot exhaust the host through the template surface: request rates are bounded per credential, the store and render dependency fail independently behind breakers, and an oversized render is refused before it runs.

## Problem

Render is the expensive operation and the store is the shared dependency, so both are abuse targets. Nothing currently bounds either, which makes the surface trivially exhaustible.

## Acceptance criteria

- [x] UAC01: A fixed window admits exactly 60 requests for one credential.
- [x] UAC02: The sixty-first request in the window is refused with 429.
- [x] UAC03: The refusal carries a retry hint, so a client knows when to try again.
- [x] UAC04: The rate refusal carries a stable problem type.
- [x] UAC05: The budget is per credential: a second credential is unaffected by the first one's quota.
- [x] UAC06: The store breaker stays closed below three consecutive failures.
- [x] UAC07: Three consecutive failures open it.
- [x] UAC08: An open breaker refuses with 503 before the handler touches the store.
- [x] UAC09: The breaker refusal carries a stable problem type.
- [x] UAC10: After the open interval the breaker is half-open and admits one probe.
- [x] UAC11: The probe is served, not refused.
- [x] UAC12: A successful probe closes the breaker again.

## Scenario contract

Given a fake clock, a counting template store, a counting executor and a production host with the `SC11` policy, When the requests hit the stated boundaries, failures and recovery interval, Then the use case records `RateLimitBoundary`, `StoreBreakerLifecycle`, `RenderBounds`, and `AdmissionOrder` with statuses, retry value, invocation counts and before/after store snapshots. Keep setup and HTTP calls visible in `SC04_EnforcesEndpointProtection.cs`; one Fact per UAC01-UAC04.

## Divergence from the backend scope

The backend surface is `/api/plugins/{**path}` behind an account, device and IP model owned by the Auth
lane. Tinytools has one credential and seven template operations, and it deliberately refuses plugin
paths (`SPEC3315-US02-SC02`). Where the backend criterion depends on accounts or devices, this scope
requires the equivalent on this surface - credential scoping, provenance of the configured key, and
untrusted client headers - rather than inventing an account system here.

Observed: 60 admitted and 1 refused with 429 in one window; the refusal carries a `Retry-After` and the
`rate-limited` problem type; a second credential is unaffected; the breaker stays `closed` after two
failures, reports `open` after three, answers 503 with the `store-unavailable` type, reports `half-open`
after the interval and serves the probe, and reports `closed` after a success.

### What changed

- `RateLimitMiddleware` enforces a fixed window of 60 requests per 60 seconds per credential, keyed by
  the presented key (or `anonymous`), with a `Retry-After` and a named problem document.
- `StoreBreaker` is a three-state breaker - closed, open after three consecutive failures, half-open
  admitting one probe after the interval - and a success closes it. `StoreBreakerMiddleware` answers
  503 before the handler runs while it is open, so a failing store is not asked again until it has had
  time to recover.
- The order is declared in `Program.cs` and is the contract: authorization, limit, breaker, handler.
  An unauthorized call never reaches the limit, and a refusal never reaches the store.

### Refinement, recorded

The inventory also carried the payload bounds and the fixed order of authorization, limit, breaker and
handler. The bounds are proven by `SPEC3329-US01-SC08` and referenced here rather than duplicated; the
order is asserted by the per-credential and probe facts plus the declared middleware order. The
breaker's open interval is configurable (`Tinytools:BreakerOpenSeconds`, default 5) so a test can
observe the transition without waiting five seconds - the default is the contract, the override is a
test seam that a deployment would only set deliberately.
