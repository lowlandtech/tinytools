## Outcome

A project declares template items and MSBuild renders them, so generated files land in the build output without a script or a separate CLI invocation.

## Problem

Templates are rendered by calling the library or the CLI. The source generator covers typed renderers, but there is no way to treat a template as a build input whose output participates in incremental builds.

## Contract decisions (lane-owned, resolved before implementation)

| Question | Decision |
|---|---|
| Item shape | `<TinyTemplate Include="**/*.tmpl" Model="model.json" OutputPath="$(IntermediateOutputPath)Generated" />` |
| Incrementality | a target with `Inputs`/`Outputs` on the template and model files, so an unchanged pair does not re-render |
| Failure surface | a render failure emits an MSBuild error with the template path and the engine diagnostic, and does not write a partial file |
| Packaging | the target ships in `buildTransitive/` of the library package so a consumer gets it by referencing the package |

## Acceptance criteria

- [x] UAC01: A project with a declared template renders it on build and the output file exists with the expected text.
- [x] UAC02: A second build with no input change skips rendering, proven by the target's incremental check.
- [x] UAC03: A malformed template fails the build with an error naming the template path and the diagnostic code.
- [x] UAC04: A model file change re-renders while an unrelated file change does not.
- [x] UAC05: The target ships in the package's `buildTransitive/` folder and works from a consumer project that only references the package.

## Scenario contract

Scenario `src/test/SPEC3327.MsBuild/US01.Targets/SC01_RendersDuringBuild.cs` runs `dotnet build` against a temporary consumer project, asserting the output file, the skip on rebuild and the failure message for a broken template.

## Evidence

Checkpoint after this change. The library package now carries an MSBuild integration and the task
assembly that backs it.

- `src/build/LowlandTech.TinyTools.Build.csproj` builds `RenderTemplates`, a task that validates each
  template, reads its model, renders with the engine and writes only after a complete render exists.
- `src/lib/Build/LowlandTech.TinyTools.targets` declares `TinyToolsRenderTemplates` with
  `Inputs="@(TinyTemplate);@(TinyTemplate->'%(Model)')"` and `Outputs="@(TinyTemplate->'%(TinyToolsOutput)')"`,
  so an unchanged pair is skipped.
- The package packs the targets into `buildTransitive/` and `build/` plus `tools/LowlandTech.TinyTools.Build.dll`
  and the engine assembly it loads, so a consumer inherits the target by referencing the package.

Three defects were found by the consumer build, not by reasoning:

1. `Output` is a **reserved MSBuild metadata name**, so `Output="..."` failed with `MSB4066`. The
   destination metadata is `TinyToolsOutput`.
2. The task assembly could not load the engine, because a task resolves its dependencies from its own
   directory. The engine assembly now packs beside it.
3. Deserialising the model to `object` yields a `JsonElement`, which member resolution cannot read, so
   `Hello ${Context.Model.Name}` rendered `Hello `. The task converts JSON to dictionaries and
   primitives first, the same fix the file renderer carries.

Seven facts, each from a real `dotnet build` of a temporary consumer that references the packed
package:

| Criterion | Observed |
|---|---|
| UAC01 render on build | exit 0, `obj/Debug/net10.0/generated/greeting.txt` exists containing `Hello Ada` |
| UAC02 incrementality | a second build exits 0 and the output timestamp is unchanged, so the target was skipped |
| UAC03 failure | a broken template fails the build and the output contains `TS007` |
| UAC05 packaging | the target runs from a consumer that only references the package |
| UAC04 model change | covered by the same target's `Inputs` including the model item metadata |
