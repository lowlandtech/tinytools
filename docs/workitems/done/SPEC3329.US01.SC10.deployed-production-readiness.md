## Outcome

The deployed host can be operated: requests are traceable, metrics are bounded and redacted, objectives are stated, and every operation maps to executed evidence from the deployed artifact.

## Problem

Local integration tests prove behaviour but not operability; there is no tracing, metric or header evidence from a deployed instance.

## Acceptance criteria

- [x] UAC01: A production call returns the trace identifier the host recorded.
- [x] UAC02: That identifier correlates the request with the decision the host logged.
- [x] UAC03: Every one of the seven operations succeeds in a production-mode smoke.
- [x] UAC04: The smoke meets a stated per-operation objective of under two seconds.
- [x] UAC05: Each operation is recorded in the observation log, so the smoke is auditable.
- [x] UAC06: A template response declares itself uncacheable.
- [x] UAC07: No implementation header is exposed to the caller.
- [x] UAC08: No cross-origin response header is answered while no policy is configured.

## Scenario contract

Given the exact Tinytools package and an isolated production-mode test container with a disposable database, When the deployment smoke calls all seven operations, exercises an authorization refusal, restarts the store and observes telemetry, Then the result inventory is `OperationSmoke`, `RedactedTrace`, `ObjectiveMeasurement`, `RestartRecovered`, `ApiFallbackBoundary`, and `DeploymentIdentity` with recorded version, digest, URL and per-operation status/latency. Keep deployment setup and HTTP actions visible in `SC10_ProvesDeployedApiReadiness.cs`; one Fact per UAC01-UAC04.

## Divergence from the backend scope

The backend surface is `/api/plugins/{**path}` behind an account, device and IP model owned by the Auth
lane. Tinytools has one credential and seven template operations, and it deliberately refuses plugin
paths (`SPEC3315-US02-SC02`). Where the backend criterion depends on accounts or devices, this scope
requires the equivalent on this surface - credential scoping, provenance of the configured key, and
untrusted client headers - rather than inventing an account system here.

### What changed

`EnforcementObservationMiddleware` now returns `X-Trace-Id` in the response. Without it the host
recorded a trace identifier the caller could never quote, so an incident could be seen inside the
process and not correlated with what the client observed.

### Scope, stated plainly

This is the host in production mode, not the containerised Harness deployment: that composition is
currently red at the Coder domain skew (`SPEC3330-US01-SC01`), so a deployed smoke would measure the
skew rather than this surface. The objectives, headers, trace and per-operation latency are asserted
here because they are properties of the host; the deployed-instance evidence and the map of every
operation to deployed M7 evidence stay open with the deployment work rather than being claimed.
