## Outcome

One command answers "does the package we published behave as documented?", by restoring that package from
the feed into a throwaway consumer and running it. It fails when the artifact is wrong, which is the only
property that makes a gate worth having.

## Why this exists

`SPEC3336-US01-SC01` shipped a watcher fix, passed **953 tests and eight consecutive acceptance runs**, and
was still wrong. Every test in this repository writes its input the way its author wrote it - one call - and
a real editor does not. A throwaway consumer project found, in ten minutes, that the "fixed" package
rendered an edit twice. That is a gap in the verification, not in the tests: the tests were right about the
behaviour they exercised.

So the artifact gets its own check, in the repository, where the next change cannot accidentally skip it.

## What it does

`eng/smoke-package.ps1`:

1. resolves the version from `Directory.Build.props` (or `-Version`);
2. refuses to run unless the feed actually carries that package;
3. generates a `net10.0` consumer that references `LowlandTech.TinyTools <version>` from the feed, with a
   `NuGet.config` that resolves that feed;
4. runs the consumer, which asserts the watcher contract:

| Case | Expected |
|---|---|
| single write | 1 render |
| staged write, 120 ms pause (inside the 250 ms settle window) | 1 render |
| staged write, 400 ms pause (past the settle window) | 2 renders - the documented boundary |
| unrelated file change | 0 renders |

5. exits non-zero if any case disagrees, and removes the consumer unless `-KeepConsumer` is passed.

The consumer program lives beside the script as `eng/smoke-package.consumer.cs.txt` rather than inside a
here-string, so it is readable, reviewable and editable as code.

## Verification

Against the version that carries the fix:

```
pwsh eng/smoke-package.ps1
-> Verifying LowlandTech.TinyTools 2026.10.8 from D:/lowlandtech/packages
   single write                                           renders=1 expected=1
   staged write, 120 ms pause (inside the settle window)  renders=1 expected=1
   staged write, 400 ms pause (past the settle window)    renders=2 expected=2
   unrelated file change                                  renders=0 expected=0
   RESULT: PASS
   The published package 2026.10.8 behaves as documented.
```

Against the version that carries the defect:

```
pwsh eng/smoke-package.ps1 -Version 2026.10.6
-> RESULT: FAIL
   The published package 2026.10.6 failed its consumer smoke with exit code 1.
   exit code 1
```

That second run is the point. A gate that cannot fail proves nothing, and this one fails on the exact
artifact that shipped the defect.

## Scope boundary

It verifies the **watcher contract** today because that is the behaviour a consumer sees and the behaviour
that regressed. It is not a general conformance suite: adding a case means adding a line to the consumer
program, and a second scenario would be a second entry there. It deliberately does not run in CI, because
CI has no workspace feed - the feed is a local artifact of the build lane, and this script is the local
counterpart of the deployed smoke a container change gets.

## Acceptance criteria

- [x] UAC01: The script resolves the version from the single version authority, or takes one explicitly.
- [x] UAC02: It refuses to run when the feed does not carry the version, rather than testing a stale package.
- [x] UAC03: It exercises the package as a consumer restores it, from the feed and not from project references.
- [x] UAC04: It passes on the corrected artifact and fails on the artifact that carries the defect.
- [x] UAC05: It leaves no consumer behind unless asked, and writes nothing into the repository.
