## Outcome

The same template renders the same text on every machine, so generated files do not change with
the developer's locale.

## Problem

`Format`-based helpers (`number`, `format`, `date`) already format with
`CultureInfo.InvariantCulture`, but interpolation of a resolved value used `object.ToString()`,
which follows the current culture. The mismatch is visible today: on a Dutch machine
`${Context.Ratio | round:2}` renders `3,14` while `${Context.Ratio | format:0.00}` renders `3.14`,
and `${Context.Value}` renders `1234,5`. Two code paths, two answers, one template.

## Contract decision (lane-owned, resolved before implementation)

**Interpolation formats numbers and dates with the invariant culture, in one place.**

| Question | Decision |
|---|---|
| Where | the single point that turns a resolved expression into text, so every helper and every bare `${...}` reaches the same rule |
| Scope | `IFormattable` values (numbers, dates, decimals); strings and booleans keep their existing text |
| Rationale | this repository generates source and data files, where a locale-dependent decimal separator silently produces different output per machine |
| Migration | a changelog entry stating that numeric interpolation is now invariant, which is the documented behaviour of `format`/`number` already |
| Not changed | helper arguments, comparisons and `where`/`orderby` parsing, which already convert invariantly |

## Acceptance criteria

- [x] UAC03: With the same culture, `${Context.Ratio | format:0.00}` keeps rendering `3.14`, so both paths now agree.
