## Outcome

Authors can edit TinyTools templates with syntax highlighting, IntelliSense, live preview and error highlighting.

## Acceptance criteria

- [ ] UAC01: Given a supported `.tmpl` document containing every syntax token the lane declares, when the editor classifier runs, `HighlightedSpans` identify each supported token and leave ordinary text unclassified.
- [ ] UAC02: Given a declared model type with public properties, when completion is requested at a supported interpolation position, `CompletionItems` contain the eligible property names and exclude unrelated members.
- [ ] UAC03: Given a document with valid syntax and deterministic model data, when the document changes, `PreviewText` corresponds to the current buffer revision and never displays output from an older revision after the current evaluation completes.
- [ ] UAC04: Given an invalid current document, `DiagnosticLocations` match the engine diagnostic code and one-based source coordinates; stale diagnostics clear after a valid edit.
- [ ] UAC05: Given a canceled or superseded preview request, `PreviewRevision` identifies the latest buffer revision and no older completion overwrites it.

## Ownership assessment (2026-10-30)

The refinement says product/ownership decisions are required and `Refined` stays false. This
records what the environment actually supports, so the decision can be made on facts:

| Question | Finding |
|---|---|
| Visual Studio available | **VS 18 Professional** is installed locally at `C:\Program Files\Microsoft Visual Studio\18\Professional`, so a VSIX could be built on this machine. |
| Visual Studio SDK | `Microsoft.VisualStudio.SDK` 17.14.40265 is on nuget.org; there is no VS 18 matching SDK version, so the extension would target a VS generation the local install does not match. |
| Editor test host | none in this repository and none in the workspace; a VS editor test host needs an installed VS instance plus the VSSDK test tooling, which cannot run on the `ubuntu-latest`, `windows-latest` or `macos-latest` CI matrix this repository uses. |
| CI impact | adding a VSIX project to `tinytools.slnx` would make the existing pipeline fail on every leg, so the repository's single gate would be traded for an extension that no CI leg can verify. |

Consequence: the lane cannot deliver UAC01-UAC05 as specified **and** keep the delivery gate
meaningful. Two options, both product decisions rather than lane decisions:

1. **Descope to an editor-agnostic syntax service in this repository** - a `netstandard2.0`
   project exposing classification spans, completion candidates from a declared model type,
   diagnostic mapping onto the engine's codes and coordinates, and revision-gated preview. It is
   fully testable with the existing xUnit gate, any editor can consume it, and the VSIX becomes a
   thin shell owned by a lane that owns Visual Studio packaging. This is my recommendation.
2. **Move the VSIX to a Visual Studio-owning lane** and keep this item as the syntax contract it
   consumes.

I am not implementing either without the decision, because option 1 changes the item's acceptance
(the refinement explicitly requires an isolated Visual Studio test host and forbids putting
editor calls in the library test project) and option 2 transfers scope to another lane.

Blocked on: coordinator/product decision between the two options above.

## Tooling probe — 2026-10-31 (the blocker is narrower than recorded)

The earlier evidence said a VSIX could not be built here: no editor test host, `Microsoft.VisualStudio.SDK`
tops out at 17.14, and a VSIX project would break every CI leg. The first and third points hold. The
second one is not a blocker for *packaging*, and that was worth measuring before offering a decision.

A throwaway `net472` project with `Microsoft.VSSDK.BuildTools` 17.14.2101, an explicit import of
`tools\VSSDK\Microsoft.VsSDK.targets`, a v2 manifest and `GeneratePkgDefFile=false` produced a
`.vsix` container **on this machine with no Visual Studio installed**:

```
dotnet msbuild "-t:Build;CreateVsixContainer" -p:Configuration=Release "-p:IntermediateOutputPath=obj\Release\\"
-> .vsix, 3800 bytes
```

Four things had to be right, and each failure named itself:

- `net472` targeting pack is present (the first build failed only on `Nullable=enable` with C# 7.3);
- the VSSDK targets are imported explicitly, because the package's own `build/` targets do not
  declare `CreateVsixContainer`;
- `IntermediateOutputPath` must be passed, or the manifest task writes to `C:\files.json`;
- the manifest needs `ProductArchitecture` and a `Prerequisites` block, and a language-client
  package sets `GeneratePkgDefFile=false` because there is no VSPackage to register.

What this changes: option 1 (an editor-agnostic language-service core plus a thin VSIX shell) no
longer needs Visual Studio to *package*. It still needs a VS test host to *verify*, which the
refinement correctly forbids putting in the library test project, and it still changes the item's
acceptance. So the decision is still the product owner's - but it is now "decide the scope and
accept that the VSIX is verified by installation, not by an automated host", not "the tooling does
not exist".
