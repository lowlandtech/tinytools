## Outcome

A plugin package says how it is deployed, and the Harness deploys what it finds. Adding a lane to a
deployment stops meaning "edit another repository's script in four places".

## Problem

Deploying Tinytools beside Coder and Builder required editing the Harness checkout:

| File | Change |
|---|---|
| `Directory.Build.props` | two version pins for the Tinytools packages |
| `src/app/LowlandTech.Harness.App.csproj` | a `TinyToolsPublishedHost` switch, a package reference, a trimmer root |
| `eng/deploy-test.ps1` | the identity list, the pin map, the client publication map, the api identity list, the api pin map, and a publish flag |

Every lane that wants to appear in a deployment repeats that, in a repository it does not own. The
Harness lane's objection is correct: committing those edits changes a delivered scope
(`HARN0008-US01-SC01`) without a source-owned scope that owns the change, so the files sit
uncommitted and the deployment cannot be reproduced from any commit.

The knowledge is also duplicated in the wrong direction: the package already declares its plugin key
and target in `lowlandtech/plugin.json`, and the feed already carries exactly one version of each
package, so the script's hand-written maps restate facts the package owns.

## Decision (lane-owned, for cross-lane review)

**A package declares its own deployment in a descriptor beside its manifest, and the Harness
discovers it.**

- `lowlandtech/deployment.json` travels in the package: `{"schemaVersion": 1, "enabled": true,
  "target": "blazor" | "backend"}`. It is deliberately **not** part of `lowlandtech/plugin.json`,
  because that document is validated with `UnmappedMemberHandling.Disallow` by the Plugins lane and a
  new member there would be refused by every reader.
- `eng/deploy-test.ps1` scans the feed for packages carrying that descriptor, reads the plugin
  key and target from the zip, and builds the identity, pin and publication sets from what it finds.
  A hand-written list remains as an explicit **override** for a package that must be admitted at a
  version other than the one the feed carries, so this is additive and reversible.
- A package without the descriptor is not discovered, so nothing is auto-admitted by accident and a
  lane opts in by shipping one file.
- The script refuses a set that carries two versions of one identity, which it already does; discovery
  does not weaken that.

## Acceptance criteria

- [ ] UAC01: A plugin package declares its deployment in `lowlandtech/deployment.json`, packed and embedded like the manifest.
- [ ] UAC02: The Harness discovers a descriptor-bearing package from the feed and admits it without a hand-written identity, pin or publication entry.
- [ ] UAC03: A package without a descriptor is not admitted, so opt-in is explicit.
- [ ] UAC04: A hand-written pin still overrides discovery, so a deployment can pin a version the feed also carries.
- [ ] UAC05: Two versions of one identity in the discovered set are refused rather than silently chosen.
- [ ] UAC06: The deployment that composes Coder, Builder and Tinytools runs from descriptors alone, and the recorded manifest lists all three.

## Scenario contract

No product behaviour in this repository: the assertion is a deployment run whose recorded manifest
lists every descriptor-bearing package, and the same run with a descriptor removed, which must list
one fewer. The check is the deployment itself (`eng/deploy-test.ps1` in the Harness checkout) plus the
recorded `eng/deployments.json`.

### Proof

With the Tinytools entries removed from the deployment script, a run against the local feed logs

```
Discovered the backend plugin LowlandTech.TinyTools.Api 2026.10.4 from its descriptor.
Discovered the blazor plugin LowlandTech.TinyTools.Frontend 2026.10.4 from its descriptor.
```

and composes:

```
admitted 3 native package(s), 3 page(s), 3 menu entry(ies):
  builder/CanvasPage, coder/CoderSessionPage, tinytools/TemplatesPage
api target admitted 4 native package(s)
```

Nothing in the script names Tinytools any more; the three pages come from the descriptors.

### Three faults found while proving it, all mine

1. `Get-PackageIdentity` is defined further down the script, so discovery had to become a function
   called after the helpers exist rather than inline code near the top.
2. `[ordered]` dictionaries do not expose their keys as properties to `Group-Object`, so every
   discovered entry grouped under an empty identity. Plain `[pscustomobject]` fixed it.
3. A function that does `$nativePackageIdentities += ...` mutates a local copy, so the pins were
   discovered and the identities were not. The discovery writes are `$script:`-scoped now, and the
   call sits before the staged and closure feed snapshots - which is what the last of the four runs
   caught.

### What is still lane-specific, and why

The compile-time package reference cannot be discovered: the Harness client has to reference the
package to publish it, so `TinyToolsPublishedHost` in `src/app/LowlandTech.Harness.App.csproj` and
its two pins in `Directory.Build.props` stay. Making that data-driven needs a generated props file
imported by the client project - a follow-up, named rather than pretended.

### The composition is red, and not because of this change

The run above needed the Coder pin at `2026.10.25`. With the Harness lane's current pin
(`2026.10.26`), publication stops at:

```
The deployment is refused: the dependency LowlandTech.Plugins.Domain
2026.10.1-20261028061559297581151 of LowlandTech.Coder.HarnessPlugin 2026.10.26 is not carried by
the closure feed
```

That is a Coder-owned version skew, present with or without descriptor discovery, and the Coder lane
was asked to settle it. This scope stays `doing` until a run with the committed pins composes all
three plugins.
