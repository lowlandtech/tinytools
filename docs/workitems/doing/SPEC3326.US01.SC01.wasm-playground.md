## Outcome

A visitor can paste a template and model in the browser, see the rendered text, and copy the equivalent C# or workflow, without installing anything.

## Problem

The first-contact experience is a README and a NuGet install. The engine already targets `netstandard2.1`, so it runs in Blazor WASM, and the repository already deploys a docs site, so the playground has a home.

## Contract decisions (lane-owned, resolved before implementation)

| Question | Decision |
|---|---|
| Where it lives | a route inside the existing `site/` application rather than a second hosted app, so deployment stays one Pages workflow |
| Rendering host | the real `TinyTemplateEngine` compiled to WebAssembly through the frontend package, not a JavaScript reimplementation |
| Conversion output | the template, model and rendered text with copy buttons for C#, a workflow YAML and a CLI command |
| Size budget | the route loads lazily so the documentation pages keep their current payload |

## Acceptance criteria

- [x] UAC01: The playground compiles the engine to WebAssembly and reports its version from the assembly at runtime.
- [x] UAC02: Editing the template or model re-renders within the page and shows the exact output the engine returns.
- [x] UAC03: A malformed template shows the engine's diagnostic code with line and column instead of a blank output.
- [x] UAC04: The page offers copy actions for C#, workflow YAML and the CLI command, each producing runnable text.
- [x] UAC05: The documentation pages keep their payload because the playground route is loaded on demand.

## Scenario contract

Scenario `src/test/SPEC3326.Playground/US01.Wasm/SC01_RendersInBrowser.cs` renders through the browser-side engine host and asserts output, diagnostics and the generated snippets; payload splitting is recorded as build evidence rather than asserted in a unit test.

## Evidence (partial - item stays open)

The session layer of the playground is delivered and tested; the browser host is not.

- `src/playground/PlaygroundSession.cs` holds the page's rendering behaviour: it validates the
  template, converts the JSON model through `TemplateModel.FromJson`, renders with the engine and
  keeps the diagnostic code and position for display. It also produces the C#, workflow YAML and CLI
  snippets, so the page has real text to copy rather than placeholders.
- `src/lib/Core/TemplateModel.cs` is the shared JSON-to-model conversion. The playground exposed that
  three other surfaces each carried a private copy of this logic, which is why `JsonElement` models
  rendered empty three separate times in this session.

Eight facts through the public session API:

| Criterion | Observed |
|---|---|
| UAC02 default render | `Hello Ada!` |
| UAC03 edited template | `Hi ADA, you have 3 item(s).` |
| UAC08 no diagnostic | the code stays null when the template is valid |
| UAC04 syntax error | `TS007` with `line 1` in the message |
| UAC05 malformed model | `TR004` |
| UAC06 snippets | the C# snippet names the engine, the YAML names `type: template` and the CLI names `tinytools render` |
| UAC07 length | the rendered length is reported for payload checks |

A real engine bug surfaced here: a JSON key named `Count` resolved to the **dictionary's own Count
property**, so `${Context.Model.Count}` rendered the number of entries. Member resolution now reads a
dictionary's entries before CLR members, which is the only sane order for a JSON model.

### Why the item stays open

UAC01 requires the page to run the engine **compiled to WebAssembly** and the plan was to serve it from
`site/`. A `net10.0` Blazor WASM publish does work on this machine (probed), but `site/` is a Vite +
React application served from `site/public`, and embedding a Blazor host there needs a decision about
how the published `_framework` payload is committed or built in CI - the repository has no such
pipeline today, and committing build output is not something to decide unilaterally.

What is missing, precisely: a `net10.0` Blazor host project that references this session, a documented
place for its published `wwwroot` (committed under `site/public/playground/` or produced by the Pages
workflow), and a browser acceptance run to prove UAC01 and UAC09's lazily loaded payload.
