## Outcome

The TinyTools server is delivered the way Coder and Builder are: a backend plugin package and a frontend contribution that a Harness deployment can compose, instead of a bespoke application only this repository can run.

PackagePath="lowlandtech\"` and embedded as a resource under `lowlandtech/plugin.json`: the api package declares `target: backend` with empty routes and contributions, the app package declares `target: blazor` with the templates route, its page contribution and its client assets.

### The binder contract, answered and applied

The Harness lane answered the question directly (`20261031T170228655548Z-dfd8df61@tinytools`): the
binder reads a package's surface from **its assembly**, not from its manifest - it scans `lib`
assemblies for a type carrying `LowlandTech.Plugins.PluginSurfaceAttribute`, and the assembly that
carries it is the one the deployment names.

`TemplatesPage` now declares `[PluginSurface("TemplatesPage", Label = "Templates", Order = 30,
ShowInNav = true)]`, matching the page identity its manifest contributes, and the package references
`LowlandTech.Plugins.Domain` at the version the Harness client pins exactly - a newer contract would
be a downgrade error (`NU1605`) at the client's restore, which is what the first attempt after the
attribute produced.

The cause is a defect in the discovery merge, now in the Harness-owned copy of `eng/deploy-test.ps1`:

```powershell
if (-not $script:nativePackagePins.Contains($entry.id)) {        # line 330
    if ($script:nativePackageIdentities -notcontains $entry.id) { $script:nativePackageIdentities += $entry.id }
```

whenever the package is discovered and let the pin decide only the version - and it belongs to the Harness
lane because it owns that file now.
