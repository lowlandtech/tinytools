## Outcome

Build-time source generation produces strongly typed template renderers without runtime template compilation.

## Acceptance criteria

- [ ] UAC01: Given a valid template item and declared model type, when a consuming project builds, `GeneratedRendererSource` has the declared model type, contains no runtime template compilation call and compiles in that consumer.
- [ ] UAC02: Given a malformed template, when compilation runs, `DiagnosticIdentity` contains a stable generator diagnostic identifier plus the source file and one-based line/column; the consumer build fails with that diagnostic.
- [ ] UAC03: Given a valid generated renderer invoked with a model, `GeneratedOutput` equals the expected output for the declared template and model.
- [ ] UAC04: Given two templates with distinct metadata and output names, `GeneratedRendererNames` are deterministic, unique and collision diagnostics name both sources rather than generating ambiguous code.
- [ ] UAC05: Given a consumer with runtime compilation packages absent, `ConsumerDependencyGraph` contains no runtime compiler dependency required by the generated renderer.
## Scenario contract

The source roadmap describes .tmpl inputs generating typed C# at build time.

## Owner decisions (phase 1 of the refinement, resolved 2026-10-30)

The unresolved prerequisite named five decisions. All five are now settled:

| Decision | Choice |
|---|---|
| Project boundary | A new analyzer project `src/generators/LowlandTech.TinyTools.Generators.csproj` targeting `netstandard2.0`, packed with `IsRoslynComponent=true` and `IncludeBuildOutput=false`, so it ships as `analyzers/dotnet/cs` and never becomes a runtime dependency of `LowlandTech.TinyTools`. |
| Input items | `<AdditionalFiles Include="**/*.tmpl" />` with optional per-item metadata: `TinyToolsModel` (fully qualified model type), `TinyToolsNamespace` (default: the consumer's root namespace plus `Templates`) and `TinyToolsOutputName` (default: derived from the file name). |
| Model declaration | The model type is named by metadata, not inferred: the generator does not guess a type from template text, so a mismatch is a compile error in generated code with the usual type name in the message. |
| Diagnostics contract | `TTG001` malformed template (carries the path plus one-based line and column from the existing syntax validator), `TTG002` missing or unresolvable `TinyToolsModel`, `TTG003` duplicate generated renderer name (names both sources), `TTG004` template item with no model metadata. Diagnostic IDs are stable and documented here; the generator never emits code that silently drops an input. |
| Minimum SDK | `Microsoft.CodeAnalysis.CSharp` 5.9.0 with the .NET 10 SDK, which is what this repository already builds with. |
| Generated shape | One static class per template with `Render(TModel model)` that calls the existing `TinyTemplateEngine` over the **embedded template text**, so no parser or compiler is required at build time and the consumer needs no runtime compilation package (UAC05 holds by construction). |

Feasibility verified: `Microsoft.CodeAnalysis.CSharp 5.9.0` resolves from nuget.org (the workspace
feed does not carry it, and an analyzer project is a build-time dependency only).

### Why this is not implemented yet

The remaining work is a second project plus a Roslyn consumer fixture: the fixture must create a
compilation, run the generator, and assert generated sources, diagnostics and the consumer
dependency graph (the refinement is explicit that the library test project alone cannot prove
generator behaviour). That is a full unit of work, and starting it with the session's remaining
budget would leave `develop` with a half-built analyzer project - the one outcome worth avoiding
in a repository whose gate must stay green. The decisions above are the expensive part; the
implementation follows as the next unit.
