## The blocker, with evidence

`SPEC3317-US01-SC01` UAC04 says *"a recorded session lists the contributed route and serves the
Templates page"*. What is measured:

| Fact | Evidence |
|---|---|
| the packages compose | deployment records: frontend activation observes `builder`, `coder`, `tinytools`; api admits four packages |
| the route and menu are published by the host | three declared pages and menus, including `tinytools/TemplatesPage` |
| the packaged assets are served | `_content/LowlandTech.TinyTools.Frontend/app.css` and `templates.js` answer 200 with the packaged byte counts |
| a session can be minted | `Auth/create-user` 200, `Auth/login-user` 200, `auth.token` returned |
| **the page renders** | **never observed** |

## Attempted workarounds and results

Each attempt is recorded in the source workitem with its message id.

| Attempt | Method | Result |
|---|---|---|
| 1 | PowerShell `POST /api/sessions` and the Auth intents | `401 A same-origin workspace request is required` - the host requires `X-GS-Request: 1` on every non-GET `/api` call |
| 2 | The same calls from inside the page with `X-GS-Request: 1`, then the sign-in form | provisioning 200 and a token; the interface stays on `/harness/login` because its sign-in is administrator-gated, and the deployment never records that credential |
| 3 | The Harness lane's own mechanism: mint a session, read `/api/plugins/frontend-projection` with the bearer token (200), then drive `/harness/templates?session=<id>` | the browser still redirects to `/harness/login?returnUrl=…`; the session query parameter does not populate the client's authentication state |

The third attempt used the owning lane's documented acceptance path
(`HARN0009.PluginSession/US02.PluginRouteAcceptance`), so it is not a blind retry. It failed for a
different reason than the first two: the client authorises a page through an authentication state, and
neither a bearer token held by the driver nor the session query parameter populates it.

## Proposed path, with decision criteria

**Option A — Harness publishes how its acceptance authenticates the client (preferred).**
Document the step, or expose it, by which `DeployedPluginRouteAcceptanceUseCase` makes the browser
authenticated for a minted session. Tinytools then runs that step, drives `/harness/templates`, and
closes UAC04 on a rendered page.
*Decision criterion:* a documented command or script a consumer lane can run against a deployment.
*Estimate:* 1 point for Tinytools once the step exists.

**Option B — refine UAC04 to what a lane can prove, and move the render to the Harness acceptance.**
UAC04 becomes: the host lists the route and menu, publishes the route to an authenticated session
(`frontend-projection` 200), and serves the package's assets. The rendered page is recorded as a
Harness-owned acceptance already covered by `HARN0009`, and linked rather than duplicated.
*Decision criterion:* agreement that the rendered-page claim belongs to the lane that owns the
deployment and its acceptance.
*Estimate:* 1 point - source and evidence only.

**Option C — Tinytools obtains an administrator credential for a deployment.** Rejected as stated:
the deployment generates its secret per run and the deploy script deliberately measures credential
leaks, so recording one to drive a test would contradict that control.

## Dependencies and risks

- The deep link `/harness/templates` answers 404 without a session; `HARN0009` attributes that to the
  Backend's `EPBE0002-US01-SC12`. Option A or B works around it with the session query parameter; it
  is not on the critical path for either.
- Risk: closing UAC04 on "assets served" would repeat the exact overclaim this lane just corrected in
  itself. Any refinement must say what is observed and name the render as unobserved.
- Risk: a lane-specific token injection would duplicate the deployment's authentication instead of
  consuming it, which is the pattern this lane has been told not to invent.
