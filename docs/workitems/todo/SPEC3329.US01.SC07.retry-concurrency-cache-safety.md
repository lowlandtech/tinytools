## Outcome

A client that retries a create does not create twice, a concurrent update is rejected rather than lost, and a cached read never serves another caller's data.

## Problem

Create has no idempotency story and update overwrites whatever it finds, which are the two ways a template library silently loses work.

## Acceptance criteria

- [ ] UAC01: `POST /api/templates` accepts an `Idempotency-Key`; the same key and payload replay the original 201, Location and resource ID for 24 hours without adding a row, while the same key with a different payload returns 409 without a second row.
- [ ] UAC02: A GET returns a strong ETag; an update with its current `If-Match` succeeds and returns a new ETag, while a second update with the stale tag returns 412 and preserves the newer stored value.
- [ ] UAC03: List and item reads declare `Cache-Control: no-store`; after create/update/delete, no prior representation is served and a subsequent uncached read reports the committed state.
## Scenario contract

Given two clients, an empty isolated database and a fixed clock, When create keys/payloads are replayed, two updates use the same entity tag, and reads follow each write, Then the results are `IdempotentReplay`, `StaleWriteRejected`, and `CacheReflectsCommittedState` with row counts, response IDs/statuses, ETags and snapshots. Keep requests and observed reads visible in `SC07_ProtectRetriesAndConcurrency.cs`; one Fact per UAC01-UAC03.

## Divergence from the backend scope

The backend surface is `/api/plugins/{**path}` behind an account, device and IP model owned by the Auth
lane. Tinytools has one credential and seven template operations, and it deliberately refuses plugin
paths (`SPEC3315-US02-SC02`). Where the backend criterion depends on accounts or devices, this scope
requires the equivalent on this surface - credential scoping, provenance of the configured key, and
untrusted client headers - rather than inventing an account system here.
