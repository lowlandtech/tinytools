## Outcome

The language server is installable from the Visual Studio extension manager, for an author who
prefers that to pointing an LSP client at a process.

## Why this is separate from M4-001

M4-001 delivered the same four capabilities through the language server, because a VSIX could not
be *verified* and would have targeted the wrong release. This item is the packaging shell only: the
behaviour already exists and is already checked.

## Blocker

The SDK prerequisite this item was written around is **satisfied**: `Microsoft.VisualStudio.SDK`
18.12.1606, the language-client support 18.12.55 and the VSSDK build tools 18.12.1606 are published,
and the package builds and packs against them.

What remains is not a version and not code. UAC02 and UAC05 require the extension to be **installed
into a running Visual Studio 18 and observed there**: the four capabilities behaving, diagnostics on a
malformed template, completion after `$` and `.`, and the preview command rendering a revision. This
lane has no Visual Studio 18 session and cannot install or drive one, and no build, archive inspection
or CI run can stand in for that observation.

- **Blocker:** an installed-editor observation that no runner in this lane can perform.
- **Resume owner:** whoever holds a Visual Studio 18 session - the workspace user, or a lane operator
  named for it. Not assignable to a runner.
- **Resume trigger:** that person installs `src/vsix` and reports the four observations, or the
  workspace decides deliberately that the extension ships unverified and UAC02/UAC05 are re-scoped to
  what a build can prove.
- **Preserved evidence:** the package builds, the container is verified by reading the archive, and CI
  is green; none of it is discardable, and none of it proves the two open criteria.

## Packaging recipe (measured 2026-10-31, no Visual Studio installed)

A throwaway `net472` project produced a `.vsix` container on this machine. Four details had to be
right, and each failure named itself:

| Detail | Why |
|---|---|
| `Microsoft.VSSDK.BuildTools` reference | provides `CreateVsixContainer` |
| explicit import of `tools\VSSDK\Microsoft.VsSDK.targets` from the package | the package's own `build/` targets do not declare that target |
| `-p:IntermediateOutputPath=obj\Release\` | otherwise the manifest task writes to `C:\files.json` |
| `GeneratePkgDefFile=false`, and a manifest with `ProductArchitecture` and `Prerequisites` | a language-client package has no VSPackage to register |

Verified transitions: `MSB4057` (target missing) -> explicit import -> `VSSDK1106` (manifest path)
-> `IntermediateOutputPath` -> `VSSDK1311` (manifest fields) -> `VSSDK1025` (pkgdef and assembly
items) -> `GeneratePkgDefFile=false` plus `-t:Build;CreateVsixContainer` -> **4800-byte `.vsix`**.


Two steps the earlier recipe did not have: `dotnet restore` has to run first (`NETSDK1004`: the assets

requested together or the container has nothing to pack.

### What still gates this item

The **editor integration**, not the packaging. A language-client extension needs the VS SDK assemblies
(`Microsoft.VisualStudio.LanguageServer.Client` and the editor contracts), and those exist only at
17.14. A VS 18-targeted VSIX that references 17.x editor assemblies may install and fail to load, and
this lane cannot prove otherwise without the SDK. The decision this item waits for is therefore
narrower and worth restating:

- **Option 1:** build the extension against 17.14 and target `[18.0,19.0)`, then verify by installing
  it into the local Visual Studio 18 and observing whether the language client activates. If it loads,
  the item is packaging work; if it does not, the extension waits for the VS 18 SDK.
- **Option 2:** keep the language-server path only (delivered in M4-001) and close this item as
  deferred until the SDK exists.

Neither is taken unilaterally: option 1 is a guess about binary compatibility that only an install can
settle, and option 2 closes the item on the user's earlier decision rather than a new one.

## Disposition — deferred on a measured gate, 2026-11-08

This item is not blocked on effort or on a decision this lane can take. It is blocked on a measurement
that is recorded in this source and has not moved since it was taken:

| Fact | Value on 2026-11-01 | Value on 2026-11-08 |
|---|---|---|
| `Microsoft.VisualStudio.SDK` (editor contracts) | 17.14.40265 | 17.14 - no VS 18 meta-package exists |
| `Microsoft.VSSDK.BuildTools` (packaging) | 18.9.820 | present - the VS 18 packaging line exists |

A VS 18-targeted container packs today: the probe in this source produced a `.vsix` with
`InstallationTarget [18.0,19.0)` and `ProductArchitecture amd64` from a throwaway `net472` project.
What does not exist is the **editor contract** a language-client extension compiles against. A VSIX that
targets 18 while referencing 17.x editor assemblies may install and fail to load, and this lane cannot
settle that from source; only an install into a real VS 18 can.

So the deciding measurement is: *does a 17.14-built language client activate in Visual Studio 18?*

- If yes, this item is packaging work and the Estimate is **3** (the recipe is proven; the remaining work
  is the extension project, its assets and one install verification).
- If no, the item waits for the VS 18 SDK and the Estimate is unchanged from its original refinement.

Deferred rather than closed as delivered: no `.vsix` ships from this lane today, and the four
capabilities have never been observed inside the editor. The language-server path itself is delivered and
verified separately (M4-001), so the editor is a convenience over a working capability, not the only way
to use the language.

What would unblock it without a compatibility gamble: a VS 18 SDK release, or a user decision to ship a
VS 17-targeted VSIX for VS 17 users and a separate VS 18 one when the SDK lands.


Recorded as deferred with that measurement rather than left open, because the measurement is the item's
whole content until the SDK ships.

## Implementation — `src/vsix`

| File | Purpose |
|---|---|
| `LowlandTech.TinyTools.Vsix.csproj` | `net472`, VS SDK 18.12.1606, LSP client 18.12.55, VSSDK build tools 18.12.1606, explicit import of `Microsoft.VsSDK.targets`, `GeneratePkgDefFile=false` |
| `source.extension.vsixmanifest` | `InstallationTarget [18.0,19.0)` with `ProductArchitecture amd64`, a `MefComponent` asset and the core-editor prerequisite |
| `TinyToolsLanguageClient.cs` | `ILanguageClient` for the `tmpl` content type, with the `.tmpl` file-extension mapping |
| `TinyToolsServerProcess.cs` | starts `server/tinytools-lsp.dll` through the dotnet host and connects over its streams |
| `PublishLanguageServer` target | publishes `src/lsp` into `obj/Release/server` and packs it as `server/**` content |

The project is deliberately **not** in `tinytools.slnx`: it targets `net472` and needs the VSSDK targets,
so adding it to the solution would break the Linux and macOS legs of CI for a package CI never ships.

## Build (verified 2026-11-18)

```
cd src/vsix
dotnet restore
dotnet msbuild "-t:Build;CreateVsixContainer" -p:Configuration=Release "-p:IntermediateOutputPath=obj\Release\"
```

Three API changes had to be handled that the 17.x recipe did not have, and each named itself:

| Error | Fix |
|---|---|
| `CS0535` `OnServerInitializeFailedAsync` | the 18.12 contract takes `ILanguageClientInitializationInfo` |
| `CS0738` return type | it returns `Task<InitializationFailureContext>`, not `Task` |
| `CS1061` on `InvokeAsync` | `StartAsync` is awaited through the handler, not chained |

### Install step for the reviewer

```
src\vsix\.vsix     (rename to LowlandTech.TinyTools.Vsix.vsix if the shell hides the empty name)
```

1. Close every Visual Studio window.
2. Double-click the package, install for Visual Studio 18 Community/Professional.
3. Open a `.tmpl` file; the status bar should show the Tinytools server, and a malformed template should
   raise a diagnostic with the engine's code and position.
4. Run the preview command and confirm the rendered revision appears.

### Editor readiness, measured 2026-11-26

The blocker above says the resume owner is "whoever holds a Visual Studio 18 session". That premise needed
checking, and it is more favourable than it reads: the session **exists on this machine**.

| Fact | Measured |
|---|---|
| Visual Studio | 18 **Professional**, `C:\Program Files\Microsoft Visual Studio\18\Professional` |
| Installer for a VSIX | `…\18\Professional\Common7\IDE\VSIXInstaller.exe` |
| Editor executable | `…\18\Professional\Common7\IDE\devenv.exe` |
| Running now | **two `devenv` processes** |

So nothing is missing from the toolchain. What remains is that installing into a running IDE and observing
the four capabilities is an interactive act on the user's editor: a VSIX install wants the IDE closed, and
this lane will not close or terminate a person's Visual Studio, exactly as it will not touch their browser.

One step, when the editor is closed:

```powershell
& "C:\Program Files\Microsoft Visual Studio\18\Professional\Common7\IDE\VSIXInstaller.exe" `
    /quiet /log "%TEMP%\tinytools-vsix-install.log" `
    "D:\lowlandtech\tinytools\src\vsix\LowlandTech.TinyTools.Vsix.vsix"
```

The container currently lands at `src/vsix/.vsix` with an empty base name, so rename it first — that is the
cosmetic defect already recorded in this source.

Then, in the editor, open a `.tmpl` file and report:

1. the language server appears in the status bar rather than a failure notification;
2. a malformed template raises a diagnostic carrying the engine's code and position;
3. completion after `$` and `.` offers the expected members;
4. the preview command renders the open document for the requested revision.

Those four observations are UAC02 and UAC05, and nothing short of them closes this item. A quiet install
alone proves installation, not behaviour, and will not be recorded as acceptance.
