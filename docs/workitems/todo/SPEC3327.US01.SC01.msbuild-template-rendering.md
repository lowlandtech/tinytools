## Outcome

A project declares template items and MSBuild renders them, so generated files land in the build output without a script or a separate CLI invocation.

## Problem

Templates are rendered by calling the library or the CLI. The source generator covers typed renderers, but there is no way to treat a template as a build input whose output participates in incremental builds.

## Contract decisions (lane-owned, resolved before implementation)

| Question | Decision |
|---|---|
| Item shape | `<TinyTemplate Include="**/*.tmpl" Model="model.json" OutputPath="$(IntermediateOutputPath)Generated" />` |
| Incrementality | a target with `Inputs`/`Outputs` on the template and model files, so an unchanged pair does not re-render |
| Failure surface | a render failure emits an MSBuild error with the template path and the engine diagnostic, and does not write a partial file |
| Packaging | the target ships in `buildTransitive/` of the library package so a consumer gets it by referencing the package |

## Acceptance criteria

- [ ] UAC01: A project with a declared template renders it on build and the output file exists with the expected text.
- [ ] UAC02: A second build with no input change skips rendering, proven by the target's incremental check.
- [ ] UAC03: A malformed template fails the build with an error naming the template path and the diagnostic code.
- [ ] UAC04: A model file change re-renders while an unrelated file change does not.
- [ ] UAC05: The target ships in the package's `buildTransitive/` folder and works from a consumer project that only references the package.

## Scenario contract

Scenario `src/test/SPEC3327.MsBuild/US01.Targets/SC01_RendersDuringBuild.cs` runs `dotnet build` against a temporary consumer project, asserting the output file, the skip on rebuild and the failure message for a broken template.
