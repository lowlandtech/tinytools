## Outcome

One declared version produces the package version, the git tag, the readme badge and every feed version, so no release can carry a version that disagrees with its tag.

## Acceptance criteria

- [ ] UAC01: Exactly one place declares the version, and every other surface derives from it or is explicitly documented as derived.
- [ ] UAC02: The tag, project version, readme badge and published feed entries agree for the next release.
- [ ] UAC03: No workflow can produce a version outside that scheme, including the stale unpadded CalVer variants recorded in `src/lib/obj/Release`.
- [ ] UAC04: Evidence records the resolved version at pack time and the corresponding feed entries.

## Scenario contract

No product behavior to test. Evidence is the pack log with the resolved version, the tag, the readme badge text and the feed listing, captured for one release candidate.

## Pickup packet

- First edit: `src/lib/LowlandTech.TinyTools.csproj` (`<Version>`), `.github/workflows/tags.yml` and `.gitea/workflows/build.yml` version computation, `readme.md` badge.
- Focused check: resolve the version through the chosen authority and compare all four surfaces.
- Delivery check: `dotnet pack` with the authority applied, plus `dotnet test tinytools.slnx -c Release`.
- Do not pick up implementation until the refinement gap below is resolved and the board Refined value is true.

## Refinement gaps

- The owner must choose the scheme (tag-driven `Version` with `-p:Version` from the tag, or CI CalVer) and the feeds that remain authoritative, because the choice defines the tag and workflow contract. The badge is also maintained by hand today and needs a stated rule.
