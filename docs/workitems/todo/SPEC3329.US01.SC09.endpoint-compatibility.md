## Outcome

A consumer pinned to a published version keeps working across additive changes, and a breaking change is either versioned or has a recorded consumer migration.

## Problem

The app reads the same contract the API exposes, so a breaking change today silently breaks the first consumer rather than a version negotiation.

## Acceptance criteria

- [ ] UAC01: Version negotiation and unsupported-version behaviour are explicit, and additive changes are distinguished from breaking ones.
- [ ] UAC02: The pinned consumers - the store, the frontend and the CLI - are proven against the published contract.
- [ ] UAC03: A breaking change records the consumer migration instead of changing the contract under a pinned consumer.

## Scenario contract

Given a pinned consumer and an additive change, when the consumer runs against the new host, then it works unchanged and the compatibility record names the version it was proven against.

The scenarios live under `src/test/SPEC3329.EndpointProtection/US01.EndpointProtection/` and follow the
shared Agentic Gherkin grammar: one scenario class per file, Given construction and When calls visible in
the scenario source, one `[Trait("UAC", "NN"), Fact]` per single-line assertion, and a unique UAC per file.

## Divergence from the backend scope

The backend surface is `/api/plugins/{**path}` behind an account, device and IP model owned by the Auth
lane. Tinytools has one credential and seven template operations, and it deliberately refuses plugin
paths (`SPEC3315-US02-SC02`). Where the backend criterion depends on accounts or devices, this scope
requires the equivalent on this surface - credential scoping, provenance of the configured key, and
untrusted client headers - rather than inventing an account system here.
