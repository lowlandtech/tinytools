## Outcome

Each of the seven template operations answers a real request with the declared status, a shape a consumer can deserialise, and the state change it promises - and a reader can see which endpoint is proven by which check.

## Problem

The endpoints exist and are exercised piecemeal by the app and store specs, but no pass proves them as an endpoint surface: status codes, boundaries and state effects are asserted incidentally, and nothing says which operation has no evidence at all.

## Acceptance criteria

- [ ] UAC01: A valid request per operation runs against an isolated host and asserts status, response schema and the resulting state or effect.
- [ ] UAC02: Malformed bodies, unknown identifiers and conflicting writes produce the declared status without partial effects or leaked data.
- [ ] UAC03: Every active operation is mapped to executed evidence; an operation with no evidence is named rather than silently covered.

## Scenario contract

Given an isolated host per operation, when each declared request runs, then the status, the body shape and the stored state are observed, and every operation appears in the coverage map.

The scenarios live under `src/test/SPEC3329.EndpointProtection/US01.EndpointProtection/` and follow the
shared Agentic Gherkin grammar: one scenario class per file, Given construction and When calls visible in
the scenario source, one `[Trait("UAC", "NN"), Fact]` per single-line assertion, and a unique UAC per file.

## Divergence from the backend scope

The backend surface is `/api/plugins/{**path}` behind an account, device and IP model owned by the Auth
lane. Tinytools has one credential and seven template operations, and it deliberately refuses plugin
paths (`SPEC3315-US02-SC02`). Where the backend criterion depends on accounts or devices, this scope
requires the equivalent on this surface - credential scoping, provenance of the configured key, and
untrusted client headers - rather than inventing an account system here.
