## Outcome

Every operation has a stated size, page and time budget, honours cancellation before it writes, and orders collections deterministically, so no request can make the host do unbounded work.

## Problem

Render and list have no declared bounds, and cancellation is passed to some calls but not proven to stop work before a side effect.

## Acceptance criteria

- [ ] UAC01: Request, page, batch and render bounds are documented and tested at the limit and one past it.
- [ ] UAC02: Collections are deterministically ordered and cursor or filter behaviour is defined.
- [ ] UAC03: A cancelled render stops before producing a side effect and reports cancellation rather than a partial result.

## Scenario contract

Given a render beyond the declared bound and a cancelled render, when both complete, then the first is refused before execution and the second leaves no output behind.

The scenarios live under `src/test/SPEC3329.EndpointProtection/US01.EndpointProtection/` and follow the
shared Agentic Gherkin grammar: one scenario class per file, Given construction and When calls visible in
the scenario source, one `[Trait("UAC", "NN"), Fact]` per single-line assertion, and a unique UAC per file.

## Divergence from the backend scope

The backend surface is `/api/plugins/{**path}` behind an account, device and IP model owned by the Auth
lane. Tinytools has one credential and seven template operations, and it deliberately refuses plugin
paths (`SPEC3315-US02-SC02`). Where the backend criterion depends on accounts or devices, this scope
requires the equivalent on this surface - credential scoping, provenance of the configured key, and
untrusted client headers - rather than inventing an account system here.
