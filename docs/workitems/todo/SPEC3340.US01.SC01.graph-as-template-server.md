## The request

> integrate graph as a template server, to not only store templates but also expose them as workflow
> steps, to generate files

Read literally that is three asks: Graph **stores** templates, Graph **offers** them as step types, and
running a step **produces files**. The third is the one with real design risk, because Graph's runtime is
deliberately stateless and pure, and writing to a filesystem is neither.

## What already exists — measured, not assumed

Both halves of this exist today in separate repositories. Nothing below is a guess; each line was read
out of the source.

### Graph has the workflow half

`D:/lowlandtech/graph` (`lowlandtech/api`) already models a workflow as graph data
(`KRNL0006-US01-SC01`), validates and executes one step (`KRNL0006-US02-SC01`), and runs a workflow from
the node that owns it (`KRNL0006-US03-SC01`):

```
(owner)         --has-workflow--> (workflow)
(workflow)      --has-step-->     (workflow-step)
(workflow-step) --has-given-->    (source:node)
(workflow-step) --has-when-->     (statemachine-action)
(workflow-step) --has-then-->     (source/edge/target)
(workflow-step) --has-handler-->  (handler) --has-result--> (target/fail)
```

A step's handler is resolved by key through `ITransitionHandlerCatalog.GetHandlerScriptAsync`, and the
handler runs as a class-defined JavaScript state machine with JSON-only input. So **the extension point for
"generate a file" already exists**: a step's handler is the seam, and no new graph vocabulary is needed.

### Tinytools has the template half

`D:/lowlandtech/tinytools` stores templates as `Template` → `TemplateVersion`
(`Id, Name, Content, Hash, DataType, Json, Text, IsValid`), renders them with `TinyTemplateEngine.Render`,
exposes them over HTTP (`GET /api/templates`, `POST /api/templates/render`,
`POST /api/templates/versions/{id}/validate`), and — the part that matters most here — already has a
**file-producing workflow runner**:

```csharp
public async Task<WorkflowResult> RunAsync(
    WorkflowDefinition workflow,
    string rootDirectory,
    object? model = null,
    Func<WorkflowStep, string, CancellationToken, Task<WorkflowStepResult>>? commandRunner = null,
    CancellationToken cancellationToken = default,
    string? templateRootDirectory = null)
```

with `WorkflowStep { Id, Type, Template, Output, Command, Args, WorkingDirectory, When, ForEach, Item }` and
`WorkflowStepResult(Id, Type, Changed, Message)`.

### The gap, stated precisely

| Half | Exists in | Shape |
|---|---|---|
| workflow model, steps, handlers, effects | Graph | data in the graph, JSON-only handlers |
| template storage and rendering | Tinytools | HTTP + entities + `TinyTemplateEngine` |
| **file emission as a step outcome** | **neither, as one thing** | Tinytools writes files but is not the graph; Graph never touches a filesystem |

Tinytools' runner writes files; Graph never does. Graph has steps; Tinytools' steps are not graph data. The
proposal is about joining those two without breaking either one's invariants.

## Design options

### Option A — a template step handler that calls the Tinytools API (recommended)

Graph gains one handler, `template`. Its script resolves the template by name through the Tinytools API and
asks *it* to render; Graph never sees template content and never writes a file itself.

```
step --has-handler--> template-render
template-render  --- HTTP ---> POST /api/templates/render { template, json }
                 <--- text ---
                 --- effect ---> file-write  (performed by the host's effect pipeline)
```

- **Why it fits:** Graph stays pure — the handler is a JSON-only script, exactly like the existing class
  handlers, and the render is a remote call. Template **storage stays in Tinytools**, where the entity,
  versioning, hashing and validation already live; Graph does not duplicate it.
- **Cost:** a deployment dependency: Graph's handler needs the Tinytools API reachable, and a render is a
  network hop. Failure modes are network-shaped, and they must be modelled (`fail` result, not an
  exception).
- **Estimate:** 5 points in Graph (handler, seed, effect, acceptance), 1 in Tinytools (nothing changes; the
  render endpoint already exists and is already protected).

### Option B — Graph stores the templates too

Templates become graph nodes: `(template) --has-version--> (template-version)`, with the content in a
property. Rendering happens in a handler, either by calling Tinytools or by porting the engine.

- **Why it is tempting:** one server, one store, no cross-service hop; templates become addressable like
  every other graph thing, and the label matrix gives them names for free.
- **Why it is expensive:** it duplicates a product surface that is already delivered and protected —
  versioning, hashing, validation, idempotency, ETags, rate limiting, 11 acceptance scenarios of endpoint
  protection — into the kernel. It also puts a *rendering engine* in the kernel, which fails the
  product-neutrality gate the workspace applies to kernel code.
- **Estimate:** 13 points, and it creates a second authority for template state.
- **Verdict:** do not do this. It is the option that looks tidier and is the one that forks the product.

### Option C — Tinytools hosts the workflow runner, Graph only stores the definition

Graph keeps the workflow model as data; Tinytools gains a step type that reads a workflow from Graph and
runs it with its existing `WorkflowRunner`.

- **Why it is cheap:** reuses the file-writing runner that already exists and is already tested.
- **Why it is wrong:** it makes Tinytools the executor of Graph's workflows, so every future workflow
  needs a Tinytools release. The ownership is backwards — Graph owns the workflow model, so Graph should
  own running it.
- **Estimate:** 3 points now, unbounded coupling later.
- **Verdict:** rejected on ownership, not on effort.

### Option D — files as effects, not as handler work

The handler produces a **descriptor** of the file (path, content, encoding) and the host's effect pipeline
writes it, exactly as it already schedules mailbox effects.

This is not an alternative to A — it is **the mechanism A should use**. Option A says *who renders*;
option D says *how the bytes reach disk* without the handler doing IO. Both are needed, and they compose.

## Recommendation

**A + D, in that order, as one scope.** Specifically:

1. A `template` step handler in Graph that renders through the Tinytools API and **produces a file
   descriptor** rather than writing anything itself.
2. A single `file-write` effect in the host's effect pipeline, with an explicit root and a refusal for any
   path outside it. Tinytools already proves this pattern: its runner refuses an output path outside the
   permitted root (`SPEC3306-US03-SC01` UAC06).
3. Graph seeds the handler so a workflow can name `template` with no authoring step.

That keeps three invariants that matter more than tidiness: Graph stays pure, Tinytools stays the single
authority for template content, and file IO happens in exactly one place with one path check.

## Dependencies and risks

| Risk | Why it bites | Mitigation |
|---|---|---|
| two authorities for template content | Option B's failure mode | Graph stores no template content at all |
| a handler doing filesystem IO | breaks the pure-step model and makes effects untestable | handler emits a descriptor; only the effect writes |
| path traversal through a template's `Output` | a workflow is data, so a malicious one could write anywhere | the effect refuses any path outside the declared root |
| render latency inside a step | a network hop per step, with retries | model as a `fail` result with the reason; do not retry inside the handler |
| deployment coupling | Graph needs the API reachable | 404/401/500 are **distinct** outcomes in the step result, not one "failed" |
| version skew | Tinytools is at `2026.10.8`; Graph pins nothing | pin the API contract, not the package: the routes are the contract |

## Estimates

| Scope | Estimate |
|---|---|
| Graph: `template` handler + seed + `file-write` effect + AppBox acceptance | 5 |
| Graph: contract tests for the three failure outcomes (missing template, refused path, unreachable API) | 2 |
| Tinytools: nothing — the render endpoint exists, is protected and is verified | 0 |
| Deployment verification once both exist | 1 |
| **Total** | **8** |

## Decision criteria

Adopt A + D when all of these hold; otherwise stop and revisit:

1. The Tinytools render endpoint is the only place template content is read — no copy enters the graph.
2. A step can fail for a missing template, a refused path and an unreachable API, and each failure is
   **distinguishable** in the step result.
3. No handler performs filesystem IO; only the effect does.
4. An AppBox journey runs a two-step workflow that writes a file into an isolated directory and asserts the
   bytes, with no prestarted host and no fixed port.
5. Nothing in `graph/src/api` learns a Tinytools-specific type; the coupling is one HTTP call with a JSON
   body.

## Verification for the implementing lane

- A workflow of two `template` steps renders two files into a temporary root and the contents match.
- A step naming an absent template fails with a reason that names the template, and writes no file.
- A step whose `Output` escapes the root fails and writes nothing outside it.
- With the API unreachable, the step fails without an unhandled exception and without a partial file.
- The graph still offers no step links as intents (`KRNL0006-US01-SC01` UAC05 must stay true).

## What this proposal is not

It is not an implementation, an authorisation, or a scope change for either lane. It was requested by the
user through the Tinytools lane, written with the Tinytools lane's facts, and is offered to the **Graph**
lane because Graph owns the workflow model and the handler catalog. Tinytools has no implementation work in
the recommended option beyond keeping its render endpoint as it is.
