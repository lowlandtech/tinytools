## The request, and the correction that shaped it

> integrate graph as a template server, to not only store templates but also expose them as workflow steps,
> to generate files

My first draft of this proposal had the dependency in the wrong place: it made Graph's `src/api` call a
Tinytools HTTP endpoint to render. The user corrected the architecture, and the correction is right:

> the graph is an api where nodes templates would store tt templates... the handler as js would only be
> stored there... a harness or client would use the handler to combine the template with data and generate
> into their fs or opfs system... why would the graph need a reference to tintytools... the harness or
> graph/app will need that reference not src/api

So: **Graph is a store and a protocol. The host renders. The reference belongs in the host, never in
`src/api`.** This rewrite follows that, and the earlier draft's HTTP-call design is withdrawn.

## What that means, measured

| Fact | Value | Consequence |
|---|---|---|
| Graph's JS engine | `Jint 4.17.0` in `src/api`, used by `TransitionStateMachine` | the api can *store* and *validate* handler scripts |
| Graph's `src/api` references Tinytools? | **no** — nothing in `graph/src` references `LowlandTech.TinyTools` | and it should stay that way |
| Tinytools core targets | `netstandard2.1`, `net8.0`, `net9.0`, `net10.0` | a host can reference it almost anywhere, including a browser host |
| Tinytools frontend | `SupportedPlatform: browser` | it already ships a browser-consumable package |
| Harness client | `Microsoft.AspNetCore.Components.WebAssembly`, **no Jint** | it has no JS engine today, and this decides who can run a handler |

That last row is the load-bearing one. If handlers are JavaScript and the client is Blazor WebAssembly,
the client cannot execute them without adding a JS runtime. So "the host runs the handler" has two
possible shapes, and they are not equally cheap.

## Shape

```
graph/src/api                          graph/app or harness/app
-------------                          ------------------------
(template) nodes                       reads the template node
  - name, content, version, hash  --->  reads the handler node (JS source)
(handler) nodes                        TinyTemplateEngine.Render(content, data)
  - name, JS source, version      --->  runs the handler for control flow
(workflow-step) nodes                  writes the result to fs / OPFS
  --has-template--> (template)
  --has-handler-->  (handler)
```

Graph never renders and never writes a file. It stores three things it already knows how to store — text
nodes, links and a workflow model — and serves them over the surface it already has.

## Options for "who runs the handler"

### Option A — the client runs the handler in the browser's own engine (recommended for harness/app)

Blazor WebAssembly can call into the browser's JavaScript through interop. The handler is JavaScript, so it
runs where JavaScript already runs natively: the browser. Tinytools renders the template server-side into
text, or the client calls `TinyTemplateEngine` directly since `netstandard2.1` supports it.

- **Why it fits:** no new dependency in `graph/src/api`; no JS engine added to a Blazor client; the handler
  runs in the runtime it was written for; the output goes to OPFS through the browser's own API.
- **Cost:** a thin interop seam on the host, and the handler's trusted-ness becomes a browser concern.
- **Estimate:** 3 points (host interop + template node read + OPFS write), 0 in Graph's api.

### Option B — the host embeds a .NET JS engine (Jint) as Graph does

The harness/app adds Jint and evaluates the handler script it fetched from Graph.

- **Why it is coherent:** the api validates a handler with Jint and the host executes it with Jint, so one
  engine semantics applies to both.
- **Why it is expensive:** Jint is ~1 MB of IL in a WebAssembly payload that already has a size budget, and
  it makes the client carry an interpreter for code the browser already has.
- **Estimate:** 5 points, plus a payload-size decision in the Harness lane.

### Option C — Graph executes the handler on a request (my withdrawn draft)

Graph calls back into a renderer at execution time.

- **Why it is wrong:** it gives `graph/src/api` a rendering dependency it should never have, and it puts
  file generation on the server when the requirement says *their* fs or OPFS. Rejected on the user's
  correction, and recorded here so it is not reintroduced by accident.

## Recommendation

**A.** Keep `graph/src/api` free of any Tinytools reference. Graph stores the template node, the handler
node and the step links. The host — Harness or another client — fetches them, renders through Tinytools and
writes to its own filesystem or OPFS in its own runtime.

Two consequences worth stating plainly:

1. **The handler cannot do IO.** Under A it runs in the browser and returns a value; the host writes the
   file. That keeps the trusted surface small and matches how Tinytools' own runner already refuses a
   path outside its root.
2. **A handler is data with the same trust weight as a script.** If the api stores JavaScript that a client
   will evaluate, then authoring a handler is a privileged act. That is a decision for Graph and the
   security lane, not for this proposal — but it must be made before A ships, and it is the reason option A
   needs a named trust boundary rather than an assumption.

## What this costs each lane

| Lane | Work | Estimate |
|---|---|---|
| Graph | template and handler node types, the step links, and a read surface for both | 3 |
| Graph | decide and document the handler trust boundary | 1 |
| Host (Harness) | fetch template + handler, render, write to fs/OPFS, interop seam | 3 |
| Tinytools | **nothing** — `TinyTemplateEngine` is already `netstandard2.1`-safe and browser-consumable | 0 |
| **Total** | | **7** |

Tinytools' estimate is genuinely zero, and that is the point of the correction: this lane already ships the
renderer in a form a client can consume.

## Decision criteria

1. `graph/src/api` still references no Tinytools package after the change.
2. A template node's content round-trips through Graph unchanged, including whitespace.
3. A host can fetch a template and a handler with one read each, without fetching the whole graph.
4. The generated file lands in the host's own fs/OPFS, and no server writes it.
5. The handler trust boundary is documented before any client evaluates a stored script.

## What I still need that is not in scope here

- **A read surface for a template + handler by key.** If fetching one template means walking the graph, the
  integration gets slow and chatty; a projection endpoint would fix it, and that is Graph's to scope.
- **Handler versioning.** A handler is code; if it can change, a workflow that produced a file yesterday may
  produce a different one today. Templates already carry versions in Tinytools; handlers need the same.
