## Why this exists

Two lanes, in separate messages on the same day, named the same blocker:

> `safe-revenue`: "instrumentation remains a prerequisite to event-based measures"

> this lane's own business case: gate 2, "the only way to learn whether anyone plays"

`SPEC3342`'s six thresholds cannot be read without events, and five of the six are event-shaped. So the
validation slice is blocked by a capability **no lane owns**. This document closes that by naming the gap
precisely, proposing a minimal vocabulary, and putting it in a repository that exists today.

## The gap, measured

The obvious assumption — "nobody instruments anything" — is **wrong**, and the correction matters:

| What exists | Where | What it is |
|---|---|---|
| protected runtime telemetry (`KRNL0047`, done) | Graph | **failure diagnostics**: a correlation id for an unexpected exception, with request data explicitly **excluded** (UAC03 asserts no credential and no body reach logs or traces) |
| template render, create, update | Tinytools | actions, not events: nothing counts them |
| deployment and activation records | Harness | one record per deployment, not per use |

So the workspace has excellent **operational** telemetry and no **product** telemetry. Those are opposites in
intent: `KRNL0047` is built to *never* carry what a user did; product analytics is built to carry nothing
else. Reusing one for the other would break the promise `KRNL0047` already made — its UAC03 explicitly
guarantees request data stays out of logs and traces.

**That is why this cannot simply be "add logging".** The privacy property that makes `KRNL0047` good is the
exact property product events must invert.

## The proposed vocabulary

Seven events, each answering one question from the business case, and no more. A first instrumented release
should be small enough to keep its privacy promise checkable.

| Event | Fields | Answers |
|---|---|---|
| `surface.opened` | surface kind (`cli`, `web`, `desktop`, `vsix`, `library`) | which host is really used |
| `template.created` | surface, template id | activation |
| `template.rendered` | surface, template id, duration ms, outcome | **use time**, what is used, the five-minute claim |
| `render.failed` | surface, error kind (never content) | where it breaks for real users |
| `session.started` | surface, subject present or anonymous | watch/use time begins |
| `session.ended` | surface, duration ms | **watch time, use time** |
| `subscription.started` / `subscription.ended` | plan key, source (`site`) | **new subs, churn** |

Deliberately absent: anything naming a template's **content**, any file path, any free text, any user name
or email. An event references a template by id, never by body.

## Where it lives, and why that is the hard part

Three candidate homes, and the choice decides whether the gate is even reachable:

| Home | For | Against |
|---|---|---|
| **Tinytools library** (`LowlandTech.TinyTools`) | one place to emit from | every consumer inherits a telemetry dependency; a template *engine* has no business shipping analytics |
| **The host** (Harness / graph app / desktop) | the host knows the surface, the subject and the session | a host-only event can't see a library render inside a plugin |
| **A shared, product-neutral emitter** | one vocabulary, many hosts | needs an owner and a new package — which the workspace rules **forbid without explicit user approval** |

**Recommendation: the host, with a thin emit seam in the library.** The library exposes a single optional
sink (`ITemplateTelemetry`, defaulted to a no-op) that a host supplies; the host decides consent, retention,
destination and subject. That keeps the library dependency-free by default, keeps the privacy decision in
the place that owns the user, and adds **no new project**.

This mirrors a pattern the workspace already trusts: `IRouteAssemblyRegistry`, `ITransitionHandlerCatalog`
and `IPluginServiceRegistration` are all pluggable seams the host fills — the library never reaches for a
concrete implementation.

## Consent and retention, stated as constraints

Not optional, and not to be designed later:

1. **No event leaves the machine before consent.** A first-run consent covers usage events; declining
   leaves the product fully functional and emits nothing.
2. **A retention window** is documented and enforced by the host, not assumed.
3. **No template content, ever** — the rule is already proven enforceable by `KRNL0047`'s UAC03, which
   asserts exactly that for request data.
4. **Anonymous is a valid state.** `session.*` works with `subject present` false; metrics that need a
   subject say so rather than pretending anonymous users don't exist.

## Who owns it

This is the decision the two messages actually need:

| Slice | Owner | Why |
|---|---|---|
| the emit seam in the library (optional, no-op by default) | **tinytools** | it is this lane's package, and it is ~1 point |
| consent, retention, destination, subject | **host lane** (Harness for the client; Graph for the app/desktop) | the host owns the user |
| the metrics that read events (dashboards, thresholds) | **safe-revenue** | they defined the six thresholds |
| the plan/subscription events' source of truth | **site lane** | `PlanCatalogue` and the Stripe checkout live there |

**The unowned part is the middle row**, and it is not a new project — it is a decision plus a config surface
inside a host that already exists.

## What would make this wrong

- **If consent cannot be implemented honestly in a desktop app**, the right answer is to measure only what a
  host can see locally and let users export it, rather than to ship silent telemetry. Stated because the
  cheap version of this proposal is exactly the dishonest version.
- **If the product is a library first**, most renders happen inside other people's hosts and the library
  seam is the only viable source — in which case the seam must be prominent, not an afterthought.
- **If Graph is meant to own product analytics**, then this is Graph's scope and the vocabulary should be
  theirs, consistent with `KRNL0047`'s privacy stance rather than beside it.

## Acceptance criteria

- [x] UAC01: The existing telemetry is measured and distinguished from product analytics, including why reusing it would break its privacy promise.
- [x] UAC02: The vocabulary is minimal, named, and each event answers a named question from the business case.
- [x] UAC03: The home of the emitter is chosen against alternatives, and the choice adds no new project.
- [x] UAC04: Consent, retention, content-exclusion and anonymity are stated as constraints rather than left to implementation.
- [x] UAC05: Each slice has a named owner, and the genuinely unowned part is identified as a decision inside an existing host.
- [x] UAC06: The assumptions that would falsify the proposal are written down, including the one where shipping this badly is worse than not shipping it.
