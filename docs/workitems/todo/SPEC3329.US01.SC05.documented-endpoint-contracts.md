## Outcome

The published contract describes what the host actually serves: stable operation identifiers, the security requirement, request and response shapes, and the error shapes - and CI fails when the host drifts from it.

## Problem

OpenAPI is mapped in development only and nothing compares it to the running host, so the document can be stale without anyone noticing.

## Acceptance criteria

- [ ] UAC01: Every operation carries a stable operationId, a security requirement, request and response schemas and an error schema.
- [ ] UAC02: CI compares the operations and schemas the host serves against the published document and fails on drift.
- [ ] UAC03: A published example is executed against an isolated host and produces the documented response.

## Scenario contract

Given the published document, when the host is asked for its runtime operations, then the two sets and their schemas agree and a deliberate change breaks the comparison.

The scenarios live under `src/test/SPEC3329.EndpointProtection/US01.EndpointProtection/` and follow the
shared Agentic Gherkin grammar: one scenario class per file, Given construction and When calls visible in
the scenario source, one `[Trait("UAC", "NN"), Fact]` per single-line assertion, and a unique UAC per file.

## Divergence from the backend scope

The backend surface is `/api/plugins/{**path}` behind an account, device and IP model owned by the Auth
lane. Tinytools has one credential and seven template operations, and it deliberately refuses plugin
paths (`SPEC3315-US02-SC02`). Where the backend criterion depends on accounts or devices, this scope
requires the equivalent on this surface - credential scoping, provenance of the configured key, and
untrusted client headers - rather than inventing an account system here.
