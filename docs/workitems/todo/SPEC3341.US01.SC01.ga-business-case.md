## The ask

Reach GA and start building an install base, preferring playing users. The desktop UI is temporary and will
end up in `graph/src/desktop` or `graph/src/app`, where this product must exist as a *client* alongside
auth, a data wallet, collaboration channels, pricing tiers, payments, marketing and content — and, most
importantly, user statistics: likes, views, watch time, use time, new subscriptions, churn.

None of that can be measured in a development shell. This document is the business case for getting there,
written against what actually exists rather than what would be nice.

## Where the product genuinely stands

Measured today, not remembered:

| Fact | Value |
|---|---|
| Shipped packages | `LowlandTech.TinyTools`, `.Core`, `.Frontend`, `.Api` at `2026.10.8` |
| Surfaces | library, CLI, language server, MSBuild generator, Razor playground, Blazor page, VS 18 VSIX |
| Tests | 953 on the CI configuration, 1 180 facts in the whole tree, 0 layout violations |
| Deployment | composes in the Harness alongside Coder and Builder; `/templates` answers 200 with a session |
| **User accounts** | **none.** The API has an API-key surface for machine callers, not users |
| **Telemetry** | **none.** A search for telemetry, analytics, tracking, pageview, usage event and consent finds nothing in product source |
| **Billing** | **none.** No pricing, plan, subscription or entitlement concept anywhere |

That last cluster is the whole business case in three lines: **there is no way to know who uses this, how
much, or whether they would pay.** A product cannot reach GA on that, and no amount of installer polish
fixes it.

## What GA actually means here

Four gates, in order, because each one makes the next measurable:

1. **Identity** — a user exists as a subject. Without it there is no "new subscriber" to count and no
   churn to measure.
2. **Instrumentation** — a use produces an event. Without it "playing users" is a guess.
3. **Commercial** — a tier exists and a payment can succeed. Without it revenue is zero however good the
   product is.
4. **Reach** — someone who is not in this workspace can install and start.

The uncomfortable ordering fact: **1 and 2 come before 3 and 4.** Pricing a product nobody is measuring is
how a launch produces no information.

## The strategic decision that precedes all of it

The user states the UI ends up in `graph/src/desktop` or `graph/src/app`. Two of those are measured facts
and they are not the same thing:

| Target | Kind | Consequence for this product |
|---|---|---|
| `graph/src/app` | `Microsoft.NET.Sdk.Web`, `net10.0` | a server-side host; the templates page would run as a Blazor server component |
| `graph/src/desktop` | `Microsoft.NET.Sdk`, `WinExe`, `net10.0-windows` | **Windows only**, which caps an install base before it starts |

`LowlandTech.TinyTools.Frontend` already declares `SupportedPlatform: browser`, and `TinyTools.Core`
targets `netstandard2.1` — so the rendering surface is portable. The desktop shell is not. **Choosing
`graph/src/desktop` as the destination decides, quietly, that the install base is Windows.** That is a
business decision wearing a technical costume, and it deserves to be made deliberately.

**Recommendation:** the product should be a **client** in the graph sense — a package that the graph's
`app` and `desktop` hosts *host*, not a codebase that moves. Then Windows desktop and later a web host are
two hosts of one client, and the install base is not capped by the first host chosen.

## What exists to build on, and what does not

Worth stating plainly, because it changes the cost of every gate:

- **Graph already has the identity spine in flight**: `KRNL0060` (deterministic ids from an HD account),
  `KRNL0066` (a key log so a path is issued once), `KRNL0064`/`KRNL0065` (data wallet, accounts, ledgers,
  channels). That is *exactly* the substrate for user channels and for a subscription ledger.
- **The site lane owns marketing and content** (`site/docs/workitems`, M1–M4: website source, nodetype
  contract, transport, content flows). This lane must not build a second content surface.
- **Nothing owns commerce.** No lane has pricing, tiers, payment or entitlement. That is a genuine hole.

So three of the four GA gates have an owner and a substrate. The commercial one does not.

## The business case, per gate

### Gate 1 — Identity: a user is a subject

**What:** the graph is the identity authority; this product consumes a subject. No second account system.

**Why it is first:** every metric in the ask — new subs, churn, watch time per user — is a per-subject
fact. A usage counter without a subject is a number, not a business.

**Cost:** 3 points here (accept a subject, scope a user's templates to it, migrate existing rows to a
system owner). Depends on `KRNL0060`/`KRNL0066` landing.

**Risk:** if this lane builds its own accounts, it forks identity and every later metric is wrong.

### Gate 2 — Instrumentation: use produces events

**What:** a small, honest event vocabulary, emitted once per action, with consent and a retention rule:

| Event | Answers |
|---|---|
| `template.rendered` | use time, what is actually used |
| `template.created` / `template.updated` | activation depth |
| `session.started` / `session.ended` | watch time, use time |
| `surface.opened` | which host is really used (web, desktop, CLI, VSIX) |
| `subscription.started` / `subscription.ended` | new subs, churn |

**Why it is second:** it is the only way to learn whether anyone plays. It is also the cheapest gate — a
week of work, not a quarter — and it is pure loss to ship GA without it, because the first cohort's
behaviour is unrecoverable.

**Design constraints that are not optional:** consent before any event leaves the machine; a documented
retention window; and no template *content* in an event, ever. A telemetry system that captures user
templates is a liability, not an asset.

**Cost:** 5 points. It has no owner today and it should probably live in the host (the graph app/desktop),
not in this library — otherwise every consumer inherits the dependency.

### Gate 3 — Commercial: a tier, and a payment that can succeed

**What:** a plan (free tier and at least one paid), an entitlement the product checks, and a payment path.
The graph's channels and ledgers (`KRNL0065`) are the natural settlement substrate, and `KRNL0068`'s
capability registration is the natural place for "this subject may publish a step".

**Why it is third:** it needs identity and instrumentation to be meaningful. Selling before measuring is
how a launch happens and teaches nothing.

**Cost:** at least 13 points, and it is currently **nobody's lane** — the single largest unowned piece in
this plan. It is also the one I would not start without an explicit commercial decision, because pricing is
not a technical judgement.

**Risk:** a subscription ledger that disagrees with the payment provider is worse than none. The "derived
balances, not stored" rule in `KRNL0065` is the right instinct and should be inherited.

### Gate 4 — Reach: someone outside this workspace can start

**What, measured against reality rather than ambition:**

| Channel | Today | Blocker |
|---|---|---|
| `dotnet add package LowlandTech.TinyTools` | published to the **workspace feed only** | public NuGet publication is not authorised |
| VS extension | builds a valid VS 18 package | unverified in an editor (`#98`) |
| CLI | works | not distributed |
| Web/desktop app | composes in the Harness | no public host, no installer |

The honest line: **there is no reachable install channel right now**, and the biggest one — public NuGet —
is a gate that has been closed by policy, not by capability. That is a decision for the user, and it is the
first thing GA needs.

**Cost:** 2 points of work once publication is authorised; the packaging is already proven.

## Marketing and content

Owned by the site lane, not this one. The business case asks for exactly one thing from it: a landing page
that can say what the product does and take a signup, because a GA with no capture surface cannot build an
install base. That is `site` M4's subject; this lane supplies the copy and the screenshots, not a second
website.

## What would make me wrong

Stated so the case can be falsified rather than defended:

- **If the product is a feature of the graph rather than a product**, then gates 3 and 4 are the graph's
  business, and this lane's only work is gate 5.
- **If playing users are means rather than end** — a way to dogfood templates before selling to teams —
  then instrumentation matters more than commerce and gate 3 can wait.
- **If Windows-only is acceptable**, gate 5's portability work is unnecessary and the install base cap is a
  choice, not a defect.

Each of those changes the total materially, which is why they are asked rather than assumed.
